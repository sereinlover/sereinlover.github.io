# 第 3 章 L1:声学特征层

L1 是整条流水线的第一层。它的输入是一个音频文件，输出是一组描述"这段声音长什么样"的数字：速度多快、什么调、有多响、响度起伏有多大、音色是集中还是分散。

这一层全部是确定性计算：同一个文件跑多少次，结果都完全一样，中间没有任何神经网络模型。用到的工具是 librosa 和 Essentia 两个音频库里现成的函数，项目做的工作主要是选参数、处理边界情况，以及在真实歌曲上发现问题后修正计算方法。

## L1 的输出字段

先看全貌。L1 一共产出 15 个字段，分成两类：

- **时间序列**：每一帧一个值（或一组值），能看出声音随时间怎么变化。帧的概念见第 2.3.2 节，L1 中相邻帧的起点相隔约 23 毫秒
- **标量**：整首歌只有一个值，是对时间序列做统计之后的结果

| 字段                  | 类型              | 含义               | 谁在用                      | 本章小节 |
| ------------------- | --------------- | ---------------- | ------------------------ | ---- |
| `duration_sec`      | 标量              | 时长（秒）            | 多处                       | 3.1  |
| `sample_rate`       | 标量              | 采样率，固定 22050     | 帧和秒的换算                   | 3.1  |
| `mfcc`              | 时间序列 `(40, T)`  | 音色的压缩描述          | 预留字段                     | 3.2  |
| `mel_spectrogram`   | 时间序列 `(128, T)` | 按人耳划分的频谱         | 谱熵（3.6）、L3 频率均衡度（5.2）    | 3.3  |
| `chroma`            | 时间序列 `(12, T)`  | 12 个音级各有多强       | 预留字段                     | 3.4  |
| `spectral_centroid` | 时间序列 `(T,)`     | 音色明暗             | 预留字段                     | 3.5  |
| `spectral_entropy`  | 标量              | 能量分布有多分散         | LLM 上下文                  | 3.6  |
| `bpm`               | 标量              | 每分钟多少拍           | LLM 上下文、结果页              | 3.7  |
| `tempo_stability`   | 标量              | 拍间隔的波动（秒）        | L3 物理精确性（5.2）、LLM 上下文    | 3.7  |
| `key`               | 标量              | 调性，如 `"G major"` | L3 结构逻辑（5.3）、LLM 上下文、结果页 | 3.8  |
| `rms`               | 时间序列 `(T,)`     | 每一帧的响度           | L2 能量感（4.8）、L3 活力张力（5.5） | 3.9  |
| `dynamic_range_db`  | 标量              | 动态范围（dB）         | L3 物理精确性（5.2）、LLM 上下文    | 3.9  |
| `silence_ratio`     | 标量              | 静音帧的比例           | LLM 上下文                  | 3.9  |
| `onset_strength`    | 时间序列 `(T,)`     | 起音强度曲线           | L2 能量感（4.8）、L3 活力张力（5.5） | 3.10 |

> 表里只列了 14 行。第 15 个字段 `audio_id` 是文件内容的哈希值，用来标识这是哪个文件（第 1.4 节），不是从声音里算出来的特征。

这张表里有 3 个保留字段，第 3.2、3.4、3.5 节会如实说明原因。

## L1 的代码结构

L1 的代码在 `apps/engine/features/` 下，按特征的类别分成 6 个文件：

| 文件 | 负责什么 | 本章小节 |
|---|---|---|
| `audio.py` | 解码音频、统一采样率、混成单声道 | 3.1 |
| `spectral.py` | MFCC、mel 频谱、chroma、谱质心、谱熵 | 3.2–3.6 |
| `temporal.py` | BPM、拍速稳定性 | 3.7 |
| `harmonic.py` | 调性 | 3.8 |
| `dynamic.py` | RMS、动态范围、静音比例、起音强度、爆发密度 | 3.9–3.10 |
| `aggregator.py` | 按顺序调用上面所有函数，组装成最终结果 | 3.11 |

数据的流向是这样的：

```
音频文件
  └─ load_audio ──→ y（22050 Hz 单声道波形）
                     ├─ spectral.py ──→ mfcc、mel_spectrogram、chroma、spectral_centroid
                     │                   └─ mel_spectrogram ──→ spectral_entropy
                     ├─ temporal.py ──→ bpm、tempo_stability
                     ├─ harmonic.py ──→ key
                     └─ dynamic.py  ──→ rms ──→ dynamic_range_db、silence_ratio
                                     └─ onset_strength
```

所有特征都从同一份波形 `y` 出发。只有两类特征是在别的特征之上再算一步：谱熵在 mel 频谱上算，动态范围和静音比例在 RMS 上算。

各个特征的原理在第 2 章已经讲过，本章不再重复推导，提到时会写明"见 2.x.x"。本章每一节按同样的顺序展开：先看代码，再解释参数为什么这样取，最后说明这个特征被谁用到。全章的例子统一用项目的测试音频 `sample.mp3`，它是一段 30 秒的咏叹调，也是网页上的 Demo 曲目之一。

## 3.1 音频加载:解码、重采样与单声道转换

### 代码

L1 的入口是 `features/audio.py: load_audio`：

```python
SAMPLE_RATE = 22050
MAX_DURATION_SEC = 3600


def load_audio(path: str) -> tuple[np.ndarray, int]:
    """Decode an audio file to a mono waveform resampled to SAMPLE_RATE."""
    y, sr = librosa.load(path, sr=SAMPLE_RATE, mono=True)
    duration_sec = len(y) / sr
    if duration_sec > MAX_DURATION_SEC:
        raise ValueError(f"audio duration {duration_sec:.1f}s exceeds the {MAX_DURATION_SEC}s limit")
    return y, int(sr)
```

`librosa.load` 这一行同时完成了三件事（见 2.2.1）：

1. **解码**：MP3、FLAC 这类文件存的是压缩后的数据，先还原成一串采样值，也就是 -1 到 1 之间的浮点数
2. **重采样**：不管原文件是 44100 Hz 还是 48000 Hz，统一转换成 22050 Hz
3. **混成单声道**：把左右两个声道取平均，合成一个声道

返回的 `y` 是一个一维 numpy 数组，`sr` 是 22050。`sample.mp3` 解码后，`y` 有 $30 \times 22050 = 661500$ 个数。

时长直接用 `len(y) / sr` 算出来：采样点总数除以每秒的采样点数，就是秒数。

### 采样率的选择

采样率决定了能记录的最高频率。按奈奎斯特定理（第 2.2.1 节），22050 Hz 最高能记录 11025 Hz。

L1 要算的特征，比如节拍、调性、音色亮度，依赖的信息主要在这个频率以下。钢琴最高音的基频约 4186 Hz，人声的基频更低。用 CD 的 44100 Hz，数据量和计算量都会翻倍，多出来的是 11025 Hz 到 22050 Hz 之间的高频细节，对这些特征几乎没有帮助。

另一个原因是 22050 Hz 是 librosa 的默认采样率。后面用到的 librosa 函数，默认参数（比如 `n_fft=2048`）都是按这个采样率设计的，在 22050 Hz 下能得到合适的时间和频率分辨率（第 2.3.3 节）。

### 单声道转换

双声道里多出来的是空间信息，比如吉他偏左、鼓偏右。L1 关心的是节奏、调性、响度、音色，这些信息在两个声道里基本一致。混成单声道后，后面所有计算的数据量都减半，结果几乎不受影响。

### 时长上限

`MAX_DURATION_SEC = 3600` 是一个防御性的上限。Gateway 处理一首歌时，要同步等 Engine 把整条流水线算完，项目里没有专门处理超长音频的设计（比如切成几段分别处理）。如果上传了一个长达数小时的音频文件，设计在第一步就报错，而不是某个特征算到一半，才因内存不足而失败。

这个常量不只 L1 在用。L2 的流派、乐器、情感、结构、和弦、拍号六个模块，都从 `features/audio.py` 引用同一个 `MAX_DURATION_SEC`，在各自解码之前先检查时长，超过就直接报错。检查用的是 `soundfile.info`，它只读文件头里记录的时长，不需要解码整个文件，几乎没有开销。张力与释放两个模块没有单独做这个检查。

> 1 小时的上限对正常歌曲来说很宽松。项目里最长的测试曲目是 29 分钟的《Art of Life》，离上限还有一半的余量。

### L1 波形与 L2 的解码

`load_audio` 解码出的 `y` 是 22050 Hz 的单声道波形。L2 的大部分模块需要别的采样率：Essentia 的流派、乐器、情感模型要 16000 Hz，不协和度计算要 44100 Hz（见 2.2.1 的表格）。所以它们不复用这份 `y`，而是各自从文件路径重新解码，直接得到自己需要的采样率。

唯一的例外是能量感，它直接复用 L1 算好的 RMS 和起音强度（第 4.8 节）。

### 音频加载测试

`tests/features/test_audio.py` 有两个用例：

- 正常读取 `sample.mp3`，检查返回的是一维、非空的数组，采样率等于 22050
- 超过时长上限时报错。这个用例没有真的往仓库里放一个超过 1 小时的音频文件，而是把 `librosa.load` 临时替换成一个直接返回"3601 秒长的数组"的假函数，用来触发报错分支

## 3.2 MFCC:频谱形状的压缩表示

### 代码

`spectral.py` 开头定义了三个所有频谱特征共用的常量：

```python
N_FFT = 2048
HOP_LENGTH = 512
N_MFCC = 40


def extract_mfcc(y: np.ndarray, sr: int) -> np.ndarray:
    """(N_MFCC, T) — per-frame timbre fingerprint."""
    return librosa.feature.mfcc(y=y, sr=sr, n_mfcc=N_MFCC, n_fft=N_FFT, hop_length=HOP_LENGTH)
```

### MFCC 参数与输出形状

- **`n_fft=2048`**：每帧取 2048 个采样点做 FFT。在 22050 Hz 下，一帧覆盖 $2048 / 22050 \approx 93$ 毫秒，频率分辨率是 $22050 / 2048 \approx 10.77$ Hz（第 2.3.3 节）。这是 librosa 的默认值
- **`hop_length=512`**：相邻两帧的起点相隔 512 个点，也就是 $512 / 22050 \approx 23$ 毫秒出一帧，每秒约 43 帧（第 2.3.2 节）。相邻两帧有 3/4 的内容重叠。这也是 librosa 的默认值
- **`n_mfcc=40`**：每帧保留 40 个 MFCC 系数（第 2.4.1 节）

输出形状是 `(40, T)`，`T` 是帧数。librosa 默认会在音频两端补零，让每一帧的中心对准 $i \times 512$ 这个位置（第 2.3.4 节），所以帧数是：

$$T = 1 + \left\lfloor \frac{\text{采样点数}}{512} \right\rfloor$$

`sample.mp3` 有 661500 个采样点，$T = 1 + \lfloor 661500 / 512 \rfloor = 1 + 1291 = 1292$ 帧。一首 3 分钟的歌，$T = 1 + \lfloor 180 \times 22050 / 512 \rfloor = 7752$ 帧。

### 共享分帧参数与时间对齐

`N_FFT` 和 `HOP_LENGTH` 是 `spectral.py` 里所有函数共用的模块常量，`dynamic.py` 里的 RMS 和起音强度也用同一个 `HOP_LENGTH = 512`。这样做的效果是：所有时间序列特征的第 $i$ 帧，指的都是同一个时刻。`sample.mp3` 的 MFCC、mel 频谱、chroma、谱质心、RMS、起音强度，全部是 1292 帧。

如果各个函数用各自的默认值，如果某个函数的参数被改了，不同特征的帧就会错开，下游按帧对齐时会出现错误。项目里有两个测试专门检查这一点：`test_spectral.py` 和 `test_dynamic.py` 里各有一个用例，断言各自文件里所有时间序列特征的帧数相同；`test_aggregator.py` 还对组装完成的整份结果再检查一次。

### MFCC 的预留用途

MFCC 提取出来后存进了 FeatureBundle（第 3.11 节），但下游没有任何地方用到它：

- L2 的分类模型有自己的输入，不用 L1 的 MFCC
- L3 的四个评分公式里没有 MFCC
- 传给 LLM 的 FeatureSummary 只有标量，没有 MFCC

它是在设计 L1 时为后续扩展预留的。比如以后要自己训练一个分类器，MFCC 是常用的输入特征。

也因为没有被使用，`n_mfcc=40` 这个取值没有被验证。librosa 的默认值是 20，语音识别里常用 13。40 能保留更多频谱细节，但对本项目来说，这个数字目前没有任何实际影响。

## 3.3 mel 频谱:128 个感知频带

### 代码

```python
N_MELS = 128


def extract_mel_spectrogram(y: np.ndarray, sr: int) -> np.ndarray:
    """(N_MELS, T)."""
    return librosa.feature.melspectrogram(y=y, sr=sr, n_mels=N_MELS, n_fft=N_FFT, hop_length=HOP_LENGTH)
```

### mel 频带数量与输出形状

`n_mels=128` 是 librosa 的默认值：把 STFT 每一帧的 1025 个频率格点，按 mel 刻度合并成 128 个频带（第 2.4.1 节）。低频的频带窄，每个约 26 Hz；高频的频带宽，每个约 280 Hz。

输出形状是 `(128, T)`。它和 MFCC 共用同样的 `n_fft`、`hop_length`，所以帧数相同，`sample.mp3` 是 `(128, 1292)`。

`melspectrogram` 返回的是功率，不是分贝。下游如果需要分贝，自己再用 `librosa.power_to_db` 转换。

### mel 频谱的独立提取与复用

MFCC 的计算过程中本来就会先算一遍 mel 频谱（第 2.4.1 节：先算 mel 频谱，再取对数、做 DCT）。但 MFCC 只返回最后的系数，中间的 mel 频谱不会留下来。mel 频谱被下游两处直接使用，所以单独算一次，作为独立字段保留：

- **谱熵**（第 3.6 节）：在 mel 频谱上计算每一帧的能量分布有多分散
- **频率均衡度**（第 5.2 节）：L3 物理精确性把 128 个频带分成低、中、高三组，换成分贝后比较三组能量差多少

和 MFCC 不同，mel 频谱是 L1 里被用得最多的时间序列之一。

## 3.4 chroma:音级分布

### 代码

```python
def extract_chroma(y: np.ndarray, sr: int) -> np.ndarray:
    """(12, T) — per-frame energy across the 12 pitch classes."""
    return librosa.feature.chroma_stft(y=y, sr=sr, n_fft=N_FFT, hop_length=HOP_LENGTH)
```

### chroma 的输出与归一化

`chroma_stft` 把 STFT 每一帧里每个频率的能量，按"属于哪个音级"加到 12 个桶里（第 2.4.2 节）。输出形状是 `(12, T)`，每一行对应一个音级，顺序是 C、C#、D……B，也就是音级 0 到 11（第 2.1.1 节）。

librosa 默认会把每一帧除以这一帧里最大的那个值。所以每一帧里最强的音级是 1，其他音级在 0 到 1 之间。这样做之后，chroma 只反映"各音级之间的比例"，不反映这一帧整体有多响。

### L1 预留的 chroma 与下游实现

L1 的 `chroma` 字段同样没有被下游使用。项目里确实有好几处需要"12 个音级各有多强"，但每一处都用了自己的实现：

| 用途 | 用的是哪种 chroma | 为什么不用 L1 这份 |
|---|---|---|
| 调性检测（3.8） | Essentia `KeyExtractor` 内部的 HPCP | 调性检测整个交给 Essentia，它接收的是波形，内部自己算音级分布 |
| 结构分段的边界检测（4.4） | MSAF 自己算的 CQT chroma：先去掉鼓声，再按拍子对齐 | MSAF 的算法只接收文件路径，内部流程是固定的 |
| 结构分段的段落聚类（4.4） | 对每个段落单独重新算一次 `chroma_stft` | 需要的是每个段落的平均值，按段落切出波形再算更直接 |
| 和弦识别（4.5） | madmom 的 DeepChroma | 神经网络有自己要求的输入：44100 Hz、每秒 10 帧 |

同一个"12 个音级各有多强"的概念，在一个项目里有四种实现。这正好对应第 2.4.2 节讲的对比：

- 手工映射的 `chroma_stft` 实现最简单，但对鼓声、泛音没有任何处理
- HPCP 和 CQT chroma 是手工规则上的改进版本：HPCP 只统计频谱峰值，CQT chroma 先去鼓声，而且频率格点按半音排列
- DeepChroma 让神经网络自己学"哪些能量才是真正在响的音"

不同模块按自己的精度需求，选了不同的实现。

## 3.5 谱质心:音色明暗

### 代码

```python
def extract_spectral_centroid(y: np.ndarray, sr: int) -> np.ndarray:
    """(T,) — per-frame energy-weighted mean frequency."""
    return librosa.feature.spectral_centroid(y=y, sr=sr, n_fft=N_FFT, hop_length=HOP_LENGTH)[0]
```

### 谱质心的含义与输出形状

谱质心是每一帧以频谱幅度为权重计算出的平均频率，单位是 Hz（公式见第 2.4.3 节）。频谱幅度更多地集中在高频时，质心较高，声音通常更明亮；集中在低频时，质心较低，声音通常更低沉。`sample.mp3` 所有帧的平均谱质心约 1040 Hz。

代码末尾的 `[0]` 是在调整形状。librosa 的 `spectral_centroid` 返回的是 `(1, T)`，第一维是为多声道输入预留的，单声道时只有一行。`[0]` 取出这一行，变成一维的 `(T,)`，和 RMS、起音强度的形状一致。

### 谱质心的使用情况

谱质心和 MFCC、chroma 一样，提取后存在 FeatureBundle 里，下游没有用到。

到这里可以总结一下：L1 在 `spectral.py` 里提取了 5 个频谱特征，其中 MFCC、chroma、谱质心 3 个没有被使用。项目把常见特征都提出来，以后扩展时可以直接用。

## 3.6 谱熵:mel 频带能量的分散程度

### 代码

```python
def compute_spectral_entropy(mel_spectrogram: np.ndarray) -> float:
    """Mean Shannon entropy of the per-frame mel energy distribution — higher
    means energy is spread across mel bands, lower means it's concentrated
    in a few (e.g. a pure tone). +1e-9 guards silent frames (all-zero energy)
    from a 0/0 NaN."""
    return float(entropy(mel_spectrogram + 1e-9, axis=0).mean())
```

`entropy` 来自 `scipy.stats`。

### 谱熵的输入:mel 频谱

和其他特征不同，这个函数的输入不是波形 `y`，而是第 3.3 节已经算好的 mel 频谱。原因有两个：

- mel 频谱的 128 个频带是按人耳的感受划分的，在它上面算出的熵，更接近"听起来能量是集中还是分散"（第 2.4.3 节）
- 直接接收算好的结果，不用再算一遍 STFT

### 谱熵的计算

一行代码里做了三件事：

1. `mel_spectrogram + 1e-9`：给每个值加一个极小的数，原因见下文
2. `entropy(..., axis=0)`：对每一列（也就是每一帧）分别计算香农熵。`scipy.stats.entropy` 会将这一帧各频带的能量分别除以该帧的总能量，得到加起来等于 1 的比例，所以代码里不需要手动归一化。结果是一个长度为 $T$ 的数组，每帧一个熵值
3. `.mean()`：对所有帧取平均，得到整首歌的一个数

`scipy.stats.entropy` 默认用自然对数，所以 128 个频带的熵，范围是 0 到 $\ln 128 \approx 4.85$。0 表示能量全部集中在一个频带里，4.85 表示能量均匀铺满所有频带。`sample.mp3` 测出的谱熵是 2.39，大致在中间。

### 静音帧的数值处理

完全静音的帧，128 个频带的能量全是 0。归一化时要除以总和，也就是 $0 / 0$，结果是 NaN（不是一个数）。NaN 有传染性：只要有一帧是 NaN，`.mean()` 的结果也会变成 NaN，整首歌的谱熵就没了。

`sample.mp3` 在 1292 帧里，实测就有 2 帧能量全为 0，出现在片头和片尾。

给每个值加上 $10^{-9}$ 之后，全零的帧变成了 128 个相等的极小值，归一化后是均匀分布，熵等于最大值 4.85。这 2 帧对整体平均的影响约为 $(4.85 - 2.39) \times 2 / 1292 \approx 0.004$，对于这段音频，平均值仍然四舍五入为 2.39。正常幅度的帧受这一常数的影响很小，接近静音的帧受影响较大。

### 谱熵在 LLM 上下文中的应用

谱熵会被放进 FeatureSummary（第 3.11 节），作为 LLM 生成解读时的上下文。选它的依据来自项目早期的一次检验：在 PMEmo 的评估数据上，谱熵和人工标注的效价相关系数 r = 0.553，和唤醒度的相关系数 r = 0.486，两者都显著（p < 0.001）。相关系数见第 2.7.6 节，效价和唤醒度见第 2.8.3 节。

这组结果表明，在参与检验的曲目中，谱熵较高的曲目倾向于获得较高的效价和唤醒度标注。乐器数量、编配和制作等因素都可能影响能量分布，单靠这次检验无法确定相关性的来源。

> 这次检验只说明谱熵和情绪有统计上的关联，项目没有用它来预测情绪。情绪由 L2 的预训练模型给出（第 4.2 节），谱熵只是作为一项补充信息交给 LLM。

## 3.7 节拍跟踪:BPM 与拍速稳定性

### 代码

`features/temporal.py` 只有一个函数：

```python
def extract_tempo(y: np.ndarray, sr: int) -> tuple[float, float]:
    """Returns (bpm, tempo_stability) — tempo_stability is the std of inter-beat
    intervals in seconds (lower = steadier tempo)."""
    tempo, beat_frames = librosa.beat.beat_track(y=y, sr=sr)
    beat_times = librosa.frames_to_time(beat_frames, sr=sr)
    # Fewer than 2 beats means no interval to measure stability from.
    tempo_stability = float(np.std(np.diff(beat_times))) if len(beat_times) > 1 else 0.0
    # librosa returns tempo as a 1-element array (supports multi-tempo estimation).
    return float(tempo[0]), tempo_stability
```

### 节拍跟踪流程

`librosa.beat.beat_track` 是第 2.6.2 节讲过的完整节拍跟踪算法，分三步：

1. 先算起音强度曲线（第 2.4.4 节）
2. 对这条曲线做自相关，估计拍子的间隔，换算成 BPM
3. 用动态规划在曲线上选出一串拍点，既尽量落在起音强的位置，又让相邻拍的间隔接近估计的拍长

它返回两样东西：`tempo` 是估出的速度，`beat_frames` 是每一拍落在第几帧。这里没有传 `hop_length`，用的是默认值 512，和其它特征一致。

### 拍速稳定性的计算

项目在 `beat_track` 的结果上做了三步处理：

1. `frames_to_time`：把拍点的帧号换成秒，第 $i$ 帧是 $i \times 512 / 22050$ 秒（第 2.3.2 节）
2. `np.diff`：相邻两拍的时间相减，得到每个拍间隔。比如拍点在 0.44、0.88、1.33 秒，拍间隔就是 0.44、0.45 秒
3. `np.std`：所有拍间隔的标准差，就是 `tempo_stability`（第 2.9.1 节）

`tempo_stability` 的单位是秒，越小越稳定。如果每一拍的间隔都完全相同，标准差就是 0。数值越大越不稳定。

`sample.mp3` 测出 BPM 为 136.0，`tempo_stability` 为 0.028 秒。

项目在 L1 验收时定过两个参照标准：鼓机制作的 EDM，速度由机器控制，`tempo_stability` 应该低于 0.02 秒；人声即兴，速度随演唱者自由伸缩，应该高于 0.1 秒。实测两者都符合。

### 拍点不足与 BPM 返回值处理

- **拍点少于 2 个**：比如一段几乎没有起音的长音。这时没有间隔可以计算，`np.diff` 会得到空数组，`np.std` 在空数组上会返回 NaN 并给出警告。代码在这种情况下直接返回 0
- **tempo 是数组**：librosa 为了支持"一首歌里有好几段速度"的估计方式，返回的 `tempo` 是一个长度为 1 的数组，不是一个数。代码用 `tempo[0]` 取出这个值，再转成 Python 的 `float`

### 时间分辨率对拍速稳定性的影响

第 2.6.2 节用节拍器声验证过：均匀节拍的 `tempo_stability` 也可能大于 0。示例中，相邻帧的间隔约为 23 毫秒，检测到的拍间隔在相邻的帧数之间变化，测得标准差约为 0.01 秒。

所以这个指标在 0.01 秒附近的差异没有实际意义，0.008 和 0.012 不能说明谁更稳定。L3 用它打分时，参照值是 0.13 秒（第 5.2 节）。

## 3.8 调性检测:HPCP 与模板匹配

### 代码

`features/harmonic.py` 只有一个函数：

```python
def extract_key(y: np.ndarray, sr: int) -> tuple[str, float]:
    """Returns (key, strength) — key e.g. "D minor", via essentia's KeyExtractor
    (accuracy-first over a hand-rolled Krumhansl template match). strength is
    essentia's 0-1 confidence in the match; callers may log it, it doesn't
    cross into FeatureSummary/FeatureBundle."""
    key, scale, strength = es.KeyExtractor(sampleRate=sr)(y)
    return f"{key} {scale}", strength
```

`es` 是 `essentia.standard`。

### KeyExtractor 的调性检测流程

`KeyExtractor` 是 Essentia 封装好的一整套调性检测流程，步骤和第 2.6.1 节讲的模板匹配相同：

1. 把音频切成帧，每帧做频谱分析
2. 在频谱上找峰值，用这些峰值算出 HPCP，也就是每一帧 12 个音级各有多强（第 2.4.2 节）
3. 把所有帧的 HPCP 加在一起，得到整首歌的音级分布
4. 和 24 个调性模板（12 个大调、12 个小调）分别计算相关程度，取最高的那个

项目没有改任何参数，全部用默认值：

- **帧长 4096**：调性检测与 L1 的 mel 频谱、chroma 等特征使用相同的采样率（22050 Hz），但每帧分析的采样点从 2048 增加到 4096，覆盖的时间也从约 93 毫秒增加到约 186 毫秒。频率格点间距等于采样率除以 FFT 点数（第 2.3.3 节），因此从约 10.77 Hz 缩小到约 5.38 Hz，正好减半。更密的频率格点有助于定位频谱峰值，而整曲调性检测对变化时刻的定位要求较低
- **模板类型 bgate**：第 2.6.1 节讲过，调性模板有很多组，bgate 是 Essentia 的默认选择
- **只在 25 Hz 到 3500 Hz 之间找频谱峰值**：这个范围覆盖了绝大多数乐器的基频和主要泛音，更高的频率主要是镲片、噪声这类和音高关系不大的成分

代码把 `sampleRate=sr` 传进去，直接使用 `load_audio` 已经解码好的 22050 Hz 波形，不需要让 Essentia 再从文件解码一次。

### 调性标签与匹配强度

`KeyExtractor` 返回三个值：

- `key`：主音，比如 `"G"`
- `scale`：调式，`"major"` 或 `"minor"`
- `strength`：0 到 1 之间的匹配置信度

代码把前两个拼成 `"G major"` 这样的字符串，和契约里 `key` 字段的格式一致。`sample.mp3` 的结果是 `"G major"`，调性匹配强度约为 0.87。

降号调会用降号写，比如 `"Eb major"`。第 2.1.1 节讲等音异名时提到的问题就来源于此：madmom 的和弦名只用升号，同一个音会被写成 `D#`，所以 L3 比较调和和弦之前，要先把两边都换成音级整数。

`strength` 只在 `aggregator.py` 里打印到日志，不放进任何数据结构，也不传给下游。

### Essentia 的选型与部署限制

项目最初的计划是手写 Krumhansl 模板匹配。第 2.6.1 节的示例代码就是它的最小版本，十几行代码就能实现。最后改用 Essentia，是因为项目对调性检测定的原则是准确率优先、有现成的库就不自己手写。Essentia 在每一步都做得更细：HPCP 只统计频谱峰值，忽略峰值之间的杂散能量；频率略有偏差的峰值，按偏差大小分摊给相邻的音级。手写 Krumhansl 模版匹配没有实现这些细节。

Engine 在 `pyproject.toml` 中将 `essentia-tensorflow` 锁定为 `2.1b6.dev1389`。这个版本为项目使用的 Python 3.12 提供了 Linux x86-64 安装包，但缺少 Linux ARM64 安装包。这个依赖既用于调性检测，也用于 L2 的流派、乐器和情感推理。

项目只发布 `linux/amd64` 的 Engine 镜像。构建和拉取镜像的部署脚本都使用 `docker-compose.base.yml`，其中将 Engine 的 `platform` 固定为 `linux/amd64`。Gateway 和 Web 则同时发布 amd64 和 ARM64 镜像。

在 ARM64 主机上，Engine 需要通过模拟运行。脚本本身只指定镜像平台，模拟环境由主机提供。使用 amd64 主机则可以原生运行 Engine。

### 调性结果的下游应用

调性字符串会进入 FeatureSummary，作为 LLM 的上下文，也显示在结果页的概览卡片上。

更重要的用途在 L3：结构逻辑评分根据这个调，生成"主、下属、属三种功能的和弦清单"，再统计识别出的和弦有多少落在清单里（第 2.1.2 节、第 5.3 节）。所以调性一旦判错，结构逻辑的覆盖率也会跟着算错。比如把 C 大调误判成 G 大调，F 大三和弦就不计入 G 大调的 T-S-D 覆盖率。

## 3.9 幅度统计:RMS、动态范围与静音比例

`dynamic.py` 里和响度有关的有三个函数：`extract_rms` 算逐帧响度，`compute_dynamic_range_db` 和 `compute_silence_ratio` 在逐帧响度上做统计。另外还有一个辅助函数 `_trim_silence_edges`。

### 逐帧 RMS

```python
HOP_LENGTH = 512


def extract_rms(y: np.ndarray, sr: int) -> np.ndarray:
    """(T,) — per-frame root-mean-square loudness."""
    return librosa.feature.rms(y=y, hop_length=HOP_LENGTH)[0]
```

RMS 是每一帧采样值的均方根，衡量这一帧有多响（第 2.2.3 节）。和 `spectral.py` 一样用 `hop_length=512`，帧和其他特征对齐；帧长用 librosa 的默认值 2048。和谱质心一样，librosa 返回 `(1, T)`，代码用 `[0]` 取成 `(T,)`。

这条 RMS 曲线有三处用途：

- 本节的动态范围和静音比例
- L2 的能量感：取它的第 90 百分位（第 4.8 节）
- L3 的活力张力：按段落分别求平均，再比较最响和最轻的段落（第 5.5 节）

### 动态范围

本项目用逐帧 RMS 的第 95 百分位数和第 5 百分位数表示音频中较响和较轻的幅度水平，并将二者的比值换算为分贝。取百分位数可以减弱个别极端帧的影响（第 2.9.1 节）。

```python
DYNAMIC_RANGE_LOW_PERCENTILE = 5
DYNAMIC_RANGE_HIGH_PERCENTILE = 95


def compute_dynamic_range_db(rms: np.ndarray) -> float:
    """95th vs 5th percentile RMS, in dB — not true min/max, see DYNAMIC_RANGE_LOW_PERCENTILE."""
    trimmed = _trim_silence_edges(rms)
    loud = np.percentile(trimmed, DYNAMIC_RANGE_HIGH_PERCENTILE)
    quiet = np.percentile(trimmed, DYNAMIC_RANGE_LOW_PERCENTILE)
    return float(20 * np.log10(loud / (quiet + 1e-9)))
```

计算百分位数之前，`_trim_silence_edges` 以全曲 RMS 峰值的 5% 为阈值，找到首个和最后一个超过阈值的帧，保留两帧之间的区间及其端点。如果没有帧超过阈值，函数返回原序列。这个处理减弱了首尾低幅度帧对统计结果的影响，同时保留曲中较轻的段落。

```python
SILENCE_RMS_RATIO = 0.05  # frames below this fraction of peak RMS count as silent


def _trim_silence_edges(rms: np.ndarray) -> np.ndarray:
    """Drops leading/trailing frames quieter than SILENCE_RMS_RATIO of peak."""
    above_threshold = np.where(rms > rms.max() * SILENCE_RMS_RATIO)[0]
    if len(above_threshold) == 0:
        return rms
    return rms[above_threshold[0] : above_threshold[-1] + 1]
```

裁剪后的 RMS 序列用于计算两个百分位数。RMS 属于振幅类量，因此使用 $20\log_{10}$ 将比值换算为分贝（第 2.2.3 节）。分母加上 $10^{-9}$ 以避免除以零（第 2.9.4 节）。以 `sample.mp3` 为例，1292 帧经裁剪后剩余 1233 帧，计算得到的动态范围约为 11.87 dB。

该结果写入 `FeatureSummary`，供 LLM 解读使用，也是 L3 物理精确性的一个子指标（第 5.2 节）。

### 静音比例

```python
def compute_silence_ratio(rms: np.ndarray) -> float:
    """Fraction of frames quieter than SILENCE_RMS_RATIO of the track's peak RMS."""
    threshold = SILENCE_RMS_RATIO * rms.max()
    return float(np.mean(rms < threshold))
```

静音比例是响度低于峰值 5% 的帧占所有帧的比例。阈值和 `_trim_silence_edges` 共用同一个常量 `SILENCE_RMS_RATIO`，所以两处对"静音"的定义完全一致。

> 代码里求比例的写法说明：`rms < threshold` 得到一个布尔数组，每一帧是 True 或 False。`np.mean` 计算平均值时，把 True 当作 1、False 当作 0，平均值就是 True 所占的比例。

注意这里用的是完整的 RMS，没有裁掉首尾。静音比例要回答的就是"这首歌里有多少时间是安静的"，片头片尾的安静也算在内。`sample.mp3` 一共有 73 帧低于峰值的 5%，$73 / 1292 \approx 0.057$，保留两位小数是 0.06。这 73 帧里，59 帧就是 `_trim_silence_edges` 在首尾裁掉的那部分，另外 14 帧零星分布在曲子中间。

静音比例只进入 FeatureSummary 作为 LLM 的上下文，L3 没有使用。项目早期的检验里，它和 PMEmo 的效价、唤醒度呈负相关（r = -0.243 和 -0.318，p < 0.01）：安静的部分越多，歌曲越倾向于低落、平静。

## 3.10 起音强度与爆发密度

### 起音强度曲线

```python
def extract_onset_strength(y: np.ndarray, sr: int) -> np.ndarray:
    """(T,) — per-frame onset novelty, higher at note/beat attacks."""
    return librosa.onset.onset_strength(y=y, sr=sr, hop_length=HOP_LENGTH)
```

这是第 2.4.4 节讲的谱通量曲线。它比较相邻两帧的频谱，只统计能量增加的部分。音符或鼓点开始发声时，曲线上可能出现峰值。帧移是 512，和其他特征一致，`sample.mp3` 的曲线有 1292 个值。

起音强度曲线作为时间序列存进 FeatureBundle，L1 不对它做统计。它的下游是爆发密度。

> `beat_track`（第 3.7 节）内部计算了起音强度，但那是函数内部的中间结果，不会返回。所以 L1 单独算了一次，作为独立字段保留。

### 爆发密度:每分钟的起音强度峰数

爆发密度衡量起音活动的密集程度。代码从起音强度曲线中筛选峰值，再按音频时长换算成平均每分钟的峰数。

```python
PEAK_HEIGHT_STD_MULTIPLIER = 0.5
PEAK_PROMINENCE_STD_MULTIPLIER = 0.5
MIN_PEAK_GAP_SEC = 0.1


def onset_burst_density(onset_strength: np.ndarray, sample_rate: int, duration_sec: float) -> float:
    """Onset-strength peaks per minute."""
    height = onset_strength.mean() + PEAK_HEIGHT_STD_MULTIPLIER * onset_strength.std()
    prominence = PEAK_PROMINENCE_STD_MULTIPLIER * onset_strength.std()
    min_gap_frames = max(1, round(MIN_PEAK_GAP_SEC * sample_rate / HOP_LENGTH))
    peaks, _ = scipy.signal.find_peaks(onset_strength, height=height, prominence=prominence, distance=min_gap_frames)
    return len(peaks) / (duration_sec / 60)
```

代码用 `scipy.signal.find_peaks` 筛选峰值（第 2.5.3 节）。筛选条件包括高度、显著性和最小间隔，具体取值见下表。

| 约束 | 取值 | 作用 |
|---|---|---|
| 高度 `height` | 曲线均值 + 0.5 倍标准差 | 峰本身要够高，过滤掉低处的小起伏 |
| 显著性 `prominence` | 0.5 倍标准差 | 峰要比周围突出，过滤掉高原上的小凸起 |
| 最小间隔 `distance` | 0.1 秒，换算成 4 帧 | 两个峰太近时只保留更高的那个 |

最小间隔的换算是 $0.1 \times 22050 / 512 \approx 4.3$，四舍五入为 4 帧。`find_peaks` 要求最小间隔至少为 1 帧，因此代码用 `max(1, ...)` 将换算结果的下限设为 1。

`sample.mp3` 的爆发密度是每分钟 216 次。

注意这个函数和本章其他函数不一样：它不是在 L1 里被调用的，L1 的 `extract_feature_bundle` 并不计算爆发密度，FeatureBundle 里也没有这个字段。它只是定义在 L1 的文件里，由 L2 的能量感和 L3 的活力张力各自调用。原因在本节最后说明。

### 基于起音强度均值和标准差的峰值阈值

不同曲目的起音强度曲线可能具有不同的数值尺度。代码以各曲目曲线的均值和标准差为依据设置阈值。高度阈值要求峰值比曲线均值至少高出 0.5 倍标准差，显著性阈值则要求峰相对周围的突出程度至少达到 0.5 倍标准差。均值和标准差反映整条曲线的分布，也会受到异常值影响。

如果将起音强度曲线的所有数值乘以同一个正数，均值、标准差和峰的显著性会按相同比例变化，最小峰间隔保持不变。因此，单独对曲线进行等比例缩放时，筛选出的峰位置不变。

### 最小峰间隔的作用

一次起音，例如一声鼓点，可能在相邻几帧形成多个峰。设置最小间隔可以减少这类重复计数。两个实际起音相隔很近时，其中一个对应的峰也可能被筛掉。因此，爆发密度是基于峰值的估计，峰数与实际起音次数可能不同。

### 共用的计算函数与参照值

爆发密度在两个地方被使用：

- L2 的能量感：响度和爆发密度各占一半（第 4.8 节）
- L3 的活力张力：跨段落动态对比和爆发密度各占一半（第 5.5 节）

两处的计算必须完全一致，否则同一首歌的"爆发密度"在两个地方会是两个数。最直接的做法是写一个函数，两边都调用它。问题是这个函数放在哪里：

- 放在 L2，L3 就要引用 L2 的代码
- 放在 L3，L2 就要引用 L3 的代码，而 L2 在流水线上排在 L3 前面，依赖方向反了

两种放法都会让 L2 和 L3 之间产生依赖。而它们都已经依赖 L1：两边用的起音强度曲线本来就来自 L1 的 FeatureBundle。所以项目把函数、三个阈值参数，以及归一化用的参照值，全部放在 L1 的 `dynamic.py` 里：

```python
# Empirical — the busiest real track measured. Same sharing rationale as the
# peak-detection params above: classifiers/energy.py and
# scoring/vital_tension.py both normalize onset_burst_density's output
# against this same reference, kept here so neither has its own copy to
# drift out of sync.
BURST_DENSITY_REFERENCE_PER_MIN = 310.0
```

L2 和 L3 都从 L1 引用，只有一份定义，不会出现改了一处、忘了另一处的情况。

校准曲目中，《Forever Love》的起音爆发密度最高，约为每分钟 279 个峰。项目将该观测值对应到约 0.9，得到经验参照值 $279 / 0.9 = 310$（第 5.1 节）。

L2 和 L3 将每分钟峰数除以 310，再把子分数限制在 0 到 1（第 2.9.4 节）。每分钟 155 个峰得 0.5，达到 310 个峰及以上得 1。`sample.mp3` 每分钟有 216 个峰，换算后约为 0.70。

## 3.11 特征汇总与传输:FeatureBundle 与 FeatureSummary

### 特征提取与结果汇总

`aggregator.py: extract_feature_bundle` 解码音频，提取声学特征，再将特征和文件信息组装成 `FeatureBundle`：

```python
def extract_feature_bundle(audio_id: str, path: str) -> FeatureBundle:
    """Runs the full L1 extractor pipeline on an audio file and assembles a FeatureBundle."""
    y, sr = load_audio(path)
    duration_sec = len(y) / sr
    mfcc = extract_mfcc(y, sr)
    mel_spectrogram = extract_mel_spectrogram(y, sr)
    chroma = extract_chroma(y, sr)
    spectral_centroid = extract_spectral_centroid(y, sr)
    spectral_entropy = compute_spectral_entropy(mel_spectrogram)
    bpm, tempo_stability = extract_tempo(y, sr)
    key, _ = extract_key(y, sr)
    rms = extract_rms(y, sr)
    onset_strength = extract_onset_strength(y, sr)
    dynamic_range_db = compute_dynamic_range_db(rms)
    silence_ratio = compute_silence_ratio(rms)
    return FeatureBundle(
        audio_id=audio_id,
        duration_sec=duration_sec,
        sample_rate=sr,
        mfcc=mfcc,
        mel_spectrogram=mel_spectrogram,
        chroma=chroma,
        spectral_centroid=spectral_centroid,
        rms=rms,
        onset_strength=onset_strength,
        bpm=bpm,
        tempo_stability=tempo_stability,
        key=key,
        dynamic_range_db=dynamic_range_db,
        spectral_entropy=spectral_entropy,
        silence_ratio=silence_ratio,
    )
```

`extract_feature_bundle` 负责按依赖顺序调用各特征计算函数，并将结果汇总为 `FeatureBundle`。各项计算由相应的模块实现。例如，`spectral.py` 根据 mel 频谱计算谱熵，`dynamic.py` 根据逐帧 RMS 计算动态范围和静音比例。这种组织方式使特征的计算规则集中在各自的模块中，便于单独维护和测试。

调用顺序里只有两处先后依赖：谱熵要在 mel 频谱之后算，动态范围和静音比例要在 RMS 之后算。其余函数之间互不依赖。第 3.10 节介绍的起音强度包含在 `FeatureBundle` 中，L2 和 L3 再根据起音强度计算爆发密度。

### FeatureBundle 的字段组成

FeatureBundle 的定义在 `contracts/contracts/types.py`，就是本章开头那张表里的全部字段：

| 类型   | 字段                                                    | `sample.mp3` 的值或形状      |
| ---- | ----------------------------------------------------- | ----------------------- |
| 基本信息 | `audio_id`、`duration_sec`、`sample_rate`               | 哈希值、30.0、22050          |
| 时间序列 | `mfcc`                                                | `(40, 1292)`            |
|      | `mel_spectrogram`                                     | `(128, 1292)`           |
|      | `chroma`                                              | `(12, 1292)`            |
|      | `spectral_centroid`、`rms`、`onset_strength`            |  `(1292,)`              |
| 标量   | `bpm`、`tempo_stability`、`key`                         | 136.0、0.028、`"G major"` |
|      | `dynamic_range_db`、`spectral_entropy`、`silence_ratio` | 11.87、2.39、0.06         |

### FeatureSummary 的跨服务传输

第 1.4 节讲过，Engine 的结果要通过 HTTP 返回给 Gateway，数据格式是 JSON。FeatureBundle 不能直接这样传，原因有两个：

- numpy 数组不能直接放进 JSON，要转成普通列表，而且转换后体积会大很多
- 时间序列的数据量很大。一首 3 分钟的歌，仅 mel 频谱就有 $128 \times 7752 \approx 99$ 万个数。Gateway 拿到这些数也没有用：它不做计算，只负责转发和存储

所以 L1 对外的接口 `/internal/extract-features` 返回的不是 FeatureBundle，而是只保留标量的 `FeatureSummary`：

```python
def build_feature_summary(bundle: FeatureBundle) -> FeatureSummary:
    """Drops the FeatureBundle's numpy time series, keeping only the wire-safe scalars."""
    return FeatureSummary(
        bpm=round(bundle.bpm, 2),
        tempo_stability=round(bundle.tempo_stability, 2),
        key=bundle.key,
        dynamic_range_db=round(bundle.dynamic_range_db, 2),
        spectral_entropy=round(bundle.spectral_entropy, 2),
        silence_ratio=round(bundle.silence_ratio, 2),
        duration_sec=round(bundle.duration_sec, 2),
    )
```

接口只有两行：

```python
@router.post("/internal/extract-features", response_model=FeatureSummary)
def extract_features(payload: ExtractFeaturesRequest) -> FeatureSummary:
    bundle = extract_feature_bundle(payload.audio_id, payload.audio_path)
    return build_feature_summary(bundle)
```

`sample.mp3` 的 FeatureSummary 是：

```python
FeatureSummary(bpm=136.0, tempo_stability=0.03, key='G major', dynamic_range_db=11.87,
               spectral_entropy=2.39, silence_ratio=0.06, duration_sec=30.0)
```

FeatureSummary 有 7 个字段：6 个特征标量，加上时长。FeatureBundle 里的 `audio_id` 不需要放进来，因为 Gateway 调用接口时自己就知道是哪个文件；`sample_rate` 固定是 22050，也不需要传。

Gateway 拿到 FeatureSummary 后，会把它存进最终的分析结果，结果页用它显示调性和 BPM。后面调用 L2、L3、L4 的接口时，Gateway 也会把它一起传过去。其中真正用到它的是 L4：FeatureSummary 会被整个转成 JSON，放进 LLM 的上下文（第 6.4 节）。

### FeatureSummary 的数值精度

`FeatureSummary` 中的数值四舍五入到两位小数，便于 LLM 引用。`FeatureBundle` 保留原始精度，供 L3 计算评分。

### L2 与 L3 如何取得逐帧特征

L2 的分类接口和 L3 的评分接口各自在 Engine 内调用 `extract_feature_bundle`，取得逐帧特征。L2 用这些数据计算能量感，L3 用它们计算美学评分。

一次完整分析会运行三次 L1。这样，各接口可以独立处理请求，代价是重复提取特征。

## 3.12 本章小结

L1 将音频文件解码为统一采样率的单声道波形，再提取 mel 频谱、RMS 和起音强度等逐帧特征，并计算 BPM、调性和动态范围等整曲结果。逐帧特征保留了随时间变化的信息，例如，后续模块可以根据段落的起止时间，从 RMS 曲线中取出各段的数据，比较它们的平均幅度。

引擎通过 `FeatureBundle` 保留完整特征，通过 `FeatureSummary` 向网关返回必要特征。L2 和 L3 的接口各自在引擎内重新提取所需特征，因此一次完整分析会运行三次 L1。这样做简化了接口之间的依赖，代价是增加了重复计算。
