# 第 4 章 L2:音乐理解层

L1 回答的是"这段声音的形状"：多响、多快、什么调、能量怎么分布。L2 回答的是"这段音乐的内容"：什么流派、什么情绪、用了哪些乐器、分成哪几段、用了哪些和弦、几拍子、听起来紧不紧张、有没有能量。

L1 的问题都有直接的计算公式。L2 的问题大多没有：没有一个公式能从波形算出"这是爵士乐"。L2 的流派、情感、乐器、和弦和拍号模块使用预训练模型。结构分段、张力与释放、能量感则根据声学特征和相应的计算规则得到结果。

## L2 的输出字段

L2 的全部输出存在名为 `UnderstandingBundle` 的数据结构里，定义在 `contracts/contracts/types.py`。它共有 15 个字段，其中 `audio_id` 用于标识音频文件，其余 14 个字段如下。

| 字段 | 类型 | 含义 | 来自哪个模块 | 谁在用 |
|---|---|---|---|---|
| `genre` | 字符串 | 第一名流派 | 流派识别（4.1） | LLM 上下文 |
| `genre_confidence` | 数 | 第一名的置信度 | 流派识别（4.1） | LLM 上下文 |
| `genre_top3` | 列表 | 前三名流派和置信度 | 流派识别（4.1） | 结果页、LLM 上下文 |
| `valence` | 数，-1 到 1 | 整首歌的效价 | 情感回归（4.2） | 结果页、LLM 上下文 |
| `arousal` | 数，0 到 1 | 整首歌的唤醒度 | 情感回归（4.2） | 结果页、LLM 上下文 |
| `emotion_labels` | 两个词 | 情绪标签，如 `wistful`、`melancholic` | 情感回归（4.2） | 结果页、LLM 上下文 |
| `emotion_arc` | 时间序列 | 每约 1.5 秒一个（效价，唤醒度）点 | 情感回归（4.2） | 结果页、L3 情感深度（5.4） |
| `instruments` | 列表 | 识别出的乐器和置信度 | 乐器识别（4.3） | 结果页、LLM 上下文 |
| `structure` | 列表 | 每一段的起止时间和类型 | 结构分段（4.4） | 结果页、L3 结构逻辑（5.3）、L3 活力张力（5.5） |
| `chords` | 列表 | 每个和弦的起止时间和名字 | 和弦识别（4.5） | 结果页、L3 结构逻辑（5.3） |
| `signature` | 字符串 | 拍号，如 `"4/4"`、`"3/4?"` | 拍号检测（4.6） | 结果页、LLM 上下文 |
| `tension` | 数，0 到 1 | 张力 | 张力与释放（4.7） | 结果页、LLM 上下文 |
| `release` | 数，0 到 1 | 释放 | 张力与释放（4.7） | 结果页、LLM 上下文 |
| `energy` | 数，0 到 1 | 能量感 | 能量感（4.8） | 结果页、LLM 上下文 |

整份 UnderstandingBundle 会原样交给 L4，作为 LLM 的上下文（第 6.4 节）。"谁在用"一列额外标出了结果页的显示，以及 L3 评分直接读取的字段。L3 只读取其中三个：`emotion_arc`、`structure`、`chords`。

## L2 的八个模块

L2 的代码在 `apps/engine/classifiers/` 下，分成八个模块：

| 模块    | 文件                        | 方法             | 解码的采样率          | 本章小节 |
| ----- | ------------------------- | -------------- | --------------- | ---- |
| 流派识别  | `genre.py`                | 预训练模型推理        | 16000 Hz        | 4.1  |
| 情感回归  | `emotion.py`              | 预训练模型推理        | 16000 Hz        | 4.2  |
| 乐器识别  | `instrument.py`           | 预训练模型推理        | 16000 Hz        | 4.3  |
| 结构分段  | `structure.py`            | 经典信号处理 + 层次聚类  | 22050 Hz        | 4.4  |
| 和弦识别  | `chord.py`                | 预训练模型 + CRF 解码 | 44100 Hz（库内部转换） | 4.5  |
| 拍号检测  | `signature.py`            | 预训练模型 + DBN 解码 | 44100 Hz（库内部转换） | 4.6  |
| 张力与释放 | `tension.py`、`release.py` | 经典信号处理         | 44100 Hz        | 4.7  |
| 能量感   | `energy.py`               | 基于 L1 特征的统计    | 不解码，复用 L1       | 4.8  |

另外还有一个共用文件 `_backbones.py`，负责加载预训练骨干模型。流派和乐器识别共用 discogs-effnet（第 4.1、4.3 节），情感回归使用 msd-musicnn（第 4.2 节）。

"预训练模型推理"的意思是：项目直接用在同一个任务上训练好的开源模型，不做任何训练（第 2.7.3 节）。

### 模块的实现与调用约定

各模块采用以下实现与调用约定。

1. **独立解码音频。** 除了能量感，每个模块都接收文件路径，而不是 L1 解码好的波形。原因是它们需要的采样率不完全相同（见上表的采样率一列），模型在什么采样率上训练，推理时就必须用同样的采样率（第 2.2.1 节）。
2. **检查时长。** 流派、情感、乐器、结构、和弦与拍号模块在解码前读取时长，并应用第 3.1 节的时长上限。分析请求也会经过 L1 的时长检查。
3. **模型只加载一次。** 使用预训练模型的模块会在首次调用时加载模型，并在后续请求中复用同一个实例。
4. **单独运行文件。** 每个文件末尾都有一个 `main` 函数，可以在命令行里直接对一首歌跑这一个模块，比如 `python -m classifiers.genre 歌曲.mp3`，方便调试。

以流派识别为例，懒加载单例的写法是这样的：

```python
_head_model: es.TensorflowPredict2D | None = None


def _load_models():
    global _head_model
    if _head_model is None:          # 只有第一次调用时为 None
        _head_model = es.TensorflowPredict2D(...)
    return _head_model               # 之后每次都返回同一个对象
```

### L2 分析接口

八个模块对外只有一个接口 `/internal/classify`，实现在 `routers/analysis.py: classify`：

```python
LONG_TRACK_THRESHOLD_SEC = 600
LONG_TRACK_MAX_WORKERS = 1
DEFAULT_MAX_WORKERS = 3


@router.post("/internal/classify", response_model=UnderstandingBundle)
def classify(payload: ClassifyRequest) -> UnderstandingBundle:
    # Each task independently decodes its own audio and runs its own model.
    # max_workers is capped below the 9 tasks submitted — running all 9 at
    # once multiplies peak memory per request nearly 9x.
    duration_sec = sf.info(payload.audio_path).duration
    max_workers = LONG_TRACK_MAX_WORKERS if duration_sec > LONG_TRACK_THRESHOLD_SEC else DEFAULT_MAX_WORKERS
    with concurrent.futures.ThreadPoolExecutor(max_workers=max_workers) as pool:
        fb_future = pool.submit(extract_feature_bundle, payload.audio_id, payload.audio_path)
        genre_future = pool.submit(classify_genre, payload.audio_path)
        instruments_future = pool.submit(classify_instruments, payload.audio_path)
        emotion_arc_future = pool.submit(model_emotion_arc, payload.audio_path)
        structure_future = pool.submit(segment_structure, payload.audio_path)
        chords_future = pool.submit(recognize_chords, payload.audio_path)
        signature_future = pool.submit(detect_signature, payload.audio_path)
        tension_future = pool.submit(compute_tension, payload.audio_path)
        release_future = pool.submit(compute_release, payload.audio_path)

        fb = fb_future.result()
        genre, genre_confidence, genre_top3 = genre_future.result()
        instruments = instruments_future.result()
        emotion_arc = emotion_arc_future.result()
        structure = structure_future.result()
        chords = chords_future.result()
        signature = signature_future.result()
        tension = tension_future.result()
        release = release_future.result()

    valence, arousal = average_emotion(emotion_arc)
    energy = compute_energy(fb)  # reuses fb's already-computed rms, no extra decode

    # Rounded to 2 decimals for the same reason as FeatureSummary and
    # scoring/_util.py's dimension_score() — this whole struct is also dumped
    # into the LLM's context (harness/orchestrator.py).
    return UnderstandingBundle(
        audio_id=payload.audio_id,
        genre=genre,
        genre_confidence=round(genre_confidence, 2),
        genre_top3=[GenreEntry(label=g.label, confidence=round(g.confidence, 2)) for g in genre_top3],
        emotion_labels=emotion_labels(valence, arousal),
        valence=round(valence, 2),
        arousal=round(arousal, 2),
        tension=round(tension, 2),
        release=round(release, 2),
        energy=round(energy, 2),
        emotion_arc=[
            EmotionPoint(timestamp_sec=round(p.timestamp_sec, 2), valence=round(p.valence, 2), arousal=round(p.arousal, 2))
            for p in emotion_arc
        ],
        signature=signature,
        instruments=[InstrumentEntry(name=i.name, confidence=round(i.confidence, 2)) for i in instruments],
        structure=[Segment(start_sec=round(s.start_sec, 2), end_sec=round(s.end_sec, 2), label=s.label) for s in structure],
        chords=[ChordEvent(start_sec=round(c.start_sec, 2), end_sec=round(c.end_sec, 2), chord=c.chord) for c in chords],
    )
```

这个接口用线程池并发执行 9 个任务：L1 的 `extract_feature_bundle`，加上前七个模块（张力和释放各算一个任务）。9 个任务全部完成后，再做两件事：

- 用情感弧线算出整首歌的效价和唤醒度（第 4.2 节）
- 用 L1 的结果算能量感（第 4.8 节）

**并发数为何设为 3**

每个任务都会把整首歌解码进内存，再加载各自的模型。限制在 3，兼顾速度和内存。

**长曲目为何串行处理**

超过 10 分钟的曲目，单个任务本身的内存占用就很大，3 个同时跑也有内存溢出的风险。这时并发数降到 1，9 个任务一个接一个地执行，确保稳定。

接口在返回前将置信度、时间戳和情感数值等保留两位小数。这些值会和 `FeatureSummary` 一起进入大模型的上下文（第 3.11、6.4 节）。

## 4.1 流派识别:预训练模型推理

### 流派识别的任务

这首歌属于什么流派？难点在于流派没有物理定义。"爵士"和"蓝调"的区别，不是某个频率高一点、某个数大一点，而是演奏习惯、和声语汇、乐器组合、录音年代综合起来的感觉。这类问题只能靠模型从大量标注好的例子里学。

### 流派识别的方案比较

流派识别是 L2 里改动最多的模块，前后换了三个方案。

#### 方案一:CLAP 文本匹配

CLAP 是一个把音频和文字映射到同一个向量空间的模型。用法是：把候选流派写成文字，比如 `"This is a jazz music track"`，分别算出音频和每段文字的向量，看音频和哪段文字最接近。这是真正的零样本方法：模型训练时没有专门学过这 10 个流派，换一套类别只需要换文字。

在 GTZAN 数据集（10 个流派，每段 30 秒）上测试，macro F1（第 2.7.6 节）只有 0.42。提示词的写法影响很大：`"This is a {genre} music track"` 得 0.424，更简单的 `"{genre} music"` 只有 0.346。项目事先定的门槛是 0.60，CLAP 没有达到。

CLAP 的预处理只看 10 秒音频，超过 10 秒时**随机**截取一段。先截取整首歌正中间的 10 秒，再交给 CLAP，保证同一首歌每次结果相同。

#### 方案二:在 GTZAN 上训练卷积网络

用 GTZAN 的标注数据自己训练一个专门的模型。模型是一个三层卷积网络，输入是 log-mel 频谱（第 2.4.1 节）。数据按 8:1:1 分层切分。归一化只用训练集的均值和标准差，避免数据泄漏（第 2.7.6 节）。训练 30 个 epoch 后，测试集 F1 达到 0.63，超过了门槛。

在 GTZAN 之外，项目另选了风格明确的真实曲目进行测试。CNN 在这一组中的识别表现低于 CLAP。

这一结果提示模型可能依赖 GTZAN 中的录音特征。与同一数据集内的测试相比，独立曲目更能检验模型能否适应不同录音和制作条件。

#### 方案三:Essentia 的预训练模型

改用在大规模真实数据上训练好的模型。在同一测试组中比较了几种开源组合。

| 方案 | 体积 / 单首耗时 |
|---|---|
| discogs-effnet + genre_discogs400（最终采用） | 20 MB / 不到 1 秒 |
| discogs-effnet + MTG-Jamendo 87 个扁平标签 | 21 MB / 不到 1 秒 |
| MAEST（更大的骨干）+ genre_discogs400 | 333 MB / 4–15 秒 |
| 两个模型融合 | 42 MB / 两倍耗时 |

"前三名命中率"是指正确流派出现在模型给出的前三名里的比例，只统计风格没有歧义的歌。综合测试组的命中情况、模型体积和推理耗时，项目选用了 discogs-effnet + genre_discogs400。

### 推理流程

```python
SAMPLE_RATE = 16000


def classify_genre(path: str) -> tuple[str, float, list[GenreEntry]]:
    if sf.info(path).duration > MAX_DURATION_SEC:
        raise ValueError(f"audio duration exceeds the {MAX_DURATION_SEC}s limit")

    embedding_model, head_model, top_levels = _load_models()

    audio = es.MonoLoader(filename=path, sampleRate=SAMPLE_RATE, resampleQuality=4)()
    embeddings = embedding_model(audio)
    predictions = head_model(embeddings)
    mean_scores = predictions.mean(axis=0)
    # ... 聚合成 15 个大类，见下文
```

逐行看：

1. **解码**：用 Essentia 的 `MonoLoader` 解码成 16000 Hz 单声道，这是模型训练时用的采样率。`resampleQuality=4` 是最高质量的重采样
2. **骨干出嵌入**：`embedding_model` 是 discogs-effnet。它先把音频算成 mel 频谱，再切成一个个 patch，每个 patch 覆盖 128 个 mel 帧（约 2 秒），相邻 patch 间隔 62 帧（约 1 秒）。每个 patch 输出一个 1280 维的嵌入向量（第 2.7.3 节）。`sample.mp3` 30 秒，得到 29 个 patch，`embeddings` 的形状是 `(29, 1280)`
3. **任务头输出分数**：`head_model` 是 genre_discogs400，对每个 patch 的嵌入输出 400 个风格分数，形状是 `(29, 400)`
4. **时间池化**：`.mean(axis=0)` 对所有 patch 取平均，得到整首歌的 400 个分数

流派问的是"整首歌总体上像什么"，所以用平均池化（第 2.7.3 节）。偶尔一段不典型的片段，不会改变总体判断。

### 400 个细分风格聚合成 15 个大类

genre_discogs400 的 400 个标签来自 Discogs 网站（一个音乐发行数据库）的风格分类，格式是"大类---细分风格"，比如 `Rock---Death Metal`、`Blues---Chicago Blues`。对普通用户来说，400 个细分风格太细了，所以项目按 `---` 前面的大类名分组：

```python
classes = json.loads(HEAD_METADATA_PATH.read_text())["classes"]
# Discogs labels are "TopLevelGenre---SubStyle" — split gives the taxonomy's own top-level genres.
_top_levels = [name.split("---")[0] for name in classes]

bucket_scores: dict[str, float] = {}
for group, score in zip(top_levels, mean_scores.tolist()):
    bucket_scores[group] = max(bucket_scores.get(group, 0.0), score)
```

第一段代码在模型加载时执行一次：读出 400 个标签名，用 `split("---")[0]` 取出每个标签的大类名。第二段对每首歌执行：遍历 400 个分数，按大类名放进对应的桶里，每个桶只保留见过的最高分。

Discogs 分类法自带的两级结构，拆完一共 15 个大类：

| 大类 | 细分风格数 | 大类 | 细分风格数 |
|---|---|---|---|
| Electronic | 106 | Funk / Soul | 15 |
| Rock | 91 | Classical | 13 |
| Latin | 35 | Non-Music | 13 |
| Folk, World, & Country | 27 | Blues | 12 |
| Hip Hop | 26 | Reggae | 11 |
| Jazz | 25 | Stage & Screen | 4 |
| Pop | 16 | Brass & Military | 3 |
| | | Children's | 3 |

**组内取最大值**

从上表可以看出，各个大类下面的细分风格数量差别很大。如果组内求和，电子乐有 106 个细分风格，每个哪怕只有很低的分数，加起来也会很高；儿童音乐只有 3 个细分风格，即使其中一个分数很高，加起来也不高。所以组内取最大值，每个大类只看自己最强的那一项，大类之间才公平。

### 流派排序与前三名的展示

```python
total = sum(bucket_scores.values())
ranked = sorted(bucket_scores.items(), key=lambda pair: -pair[1])
top3 = [GenreEntry(label=name, confidence=score / total) for name, score in ranked[:3]]
return top3[0].label, top3[0].confidence, top3
```

15 个大类的分数先求总和，按分数从高到低排序，取前三名，每个分数除以总和作为置信度。返回值对应 UnderstandingBundle 的三个字段：第一名的名字 `genre`、第一名的置信度 `genre_confidence`、前三名的列表 `genre_top3`。

这里要注意，模型的训练形式和项目的展示形式不一样（第 2.7.2 节）。genre_discogs400 每个风格的输出是独立的 sigmoid，400 个风格各自判断"像不像"，因为一首歌本来就可以同时属于"摇滚"和"流行"。项目展示时把它包装成了排序加归一化的形式，15 个置信度加起来等于 1，看起来像一个概率分布。所以界面上的"置信度"应该理解为"在 15 个大类里的相对占比"，而不是模型输出的原始概率。

`sample.mp3` 的结果是 Classical 0.67、Stage & Screen 0.11、Folk, World, & Country 0.08。

### 流派与乐器共用的骨干模型

乐器识别（第 4.3 节）用的是同一个 discogs-effnet 骨干，只是换了一个任务头。如果两个模块各自加载一份，内存里就会有两份完全相同的模型权重。所以骨干的加载单独放在 `classifiers/_backbones.py` 里，做成模块之间共用的单例：

```python
_discogs_effnet_model: es.TensorflowPredictEffnetDiscogs | None = None


def get_discogs_effnet_model() -> es.TensorflowPredictEffnetDiscogs:
    global _discogs_effnet_model
    if _discogs_effnet_model is None:
        _discogs_effnet_model = es.TensorflowPredictEffnetDiscogs(graphFilename=str(_DISCOGS_EFFNET_MODEL_PATH), output="PartitionedCall:1")
    return _discogs_effnet_model
```

情感回归用的 msd-musicnn 骨干，也在同一个文件里用同样的方式加载（`get_msd_musicnn_model`）。任务头只被独立的模块使用，留在各自的文件里加载。

`output="PartitionedCall:1"` 指定取模型内部哪一层的输出。discogs-effnet 本身也是一个分类模型，最后一层输出它自己的分类结果；这里要的是最后一层之前的嵌入向量，交给项目自己选的任务头。

> 模型文件（骨干 18 MB、流派任务头 2 MB）不放进 Git 仓库，用 `make models` 下载，构建 Docker 镜像时会自动下载。

## 4.2 情感回归:效价与唤醒度

### 情感回归的任务

这首歌听起来是什么情绪？项目用的是效价-唤醒模型（第 2.8.3 节）：效价表示正面还是负面，唤醒度表示激动还是平静。和流派不同，这是一个回归问题，输出是两个连续的数，而不是类别（第 2.7.2 节）。

除了整首歌的情绪，项目还要一条随时间变化的**情感弧线**：每隔一小段时间画一个点，能看到情绪怎么起伏。L3 的情感深度评分（第 5.4 节）就是基于这条弧线计算的。

### 情感回归模型

情感模块用 msd-musicnn 骨干，加上一个在 DEAM 数据集上训练好的回归头 `deam-msd-musicnn-2`。DEAM 是一个音乐情感数据集，人工给每首歌的效价和唤醒度打了分。项目拿来直接推理。

模型的核心调用只有一行，放在 `_predict_patches` 里：

```python
SAMPLE_RATE = 16000


def _predict_patches(path: str) -> np.ndarray:
    """Shared embedding+head pipeline — classify_emotion averages the
    resulting per-patch predictions, model_emotion_arc keeps them as a
    time series. Raw values are on DEAM's 1-9 scale, not yet rescaled."""
    if sf.info(path).duration > MAX_DURATION_SEC:
        raise ValueError(f"audio duration exceeds the {MAX_DURATION_SEC}s limit")

    embedding_model, head_model = _load_models()
    audio = es.MonoLoader(filename=path, sampleRate=SAMPLE_RATE, resampleQuality=4)()
    return head_model(embedding_model(audio))
```

和流派一样，先解码成 16000 Hz，骨干对每个 patch 输出嵌入向量，任务头对每个 patch 输出两个数。返回的是一个 `(patch 数, 2)` 的数组，每一行是一个 patch 的（效价，唤醒度），数值在 DEAM 的 1 到 9 分制上。

### 逐片段预测与情感弧线

项目最初的计划是"滑动窗口"：把歌切成 5 秒一段、每隔 1 秒切一次，每段单独跑一遍情感模型，把每段的结果连起来就是弧线。

但 musicnn 本身就是按 patch 处理音频的：每个 patch 覆盖 187 个 mel 帧（约 3 秒），相邻 patch 间隔 93 帧。模型一次推理就已经得到了每个 patch 的结果。计算整首歌情绪的做法，是对这些结果求平均，丢掉了时间信息。情感弧线需要的正是对结果平均之前的那一步。

patch 之间的时间间隔由三个参数决定：

```python
PATCH_HOP_MEL_FRAMES = 93
MEL_HOP_LENGTH = 256
PATCH_HOP_SEC = PATCH_HOP_MEL_FRAMES * MEL_HOP_LENGTH / SAMPLE_RATE
```

相邻 patch 相隔 93 个 mel 帧，每个 mel 帧前进 256 个采样点，采样率 16000 Hz，所以间隔是 $93 \times 256 / 16000 = 1.488$ 秒（第 2.3.2 节的帧秒换算）。第 $i$ 个 patch 的时间戳就是 $i \times 1.488$ 秒。`sample.mp3` 的 patch 数是 19 个，时间戳从 0 到 26.8 秒。

弧线上的每个点，由 `_points_from_predictions` 生成：

```python
def _points_from_predictions(predictions: np.ndarray) -> list[EmotionPoint]:
    return [
        EmotionPoint(
            timestamp_sec=i * PATCH_HOP_SEC,
            valence=_rescale(float(raw_valence), -1.0, 1.0),
            arousal=_rescale(float(raw_arousal), 0.0, 1.0),
        )
        for i, (raw_valence, raw_arousal) in enumerate(predictions)
    ]


def model_emotion_arc(path: str) -> list[EmotionPoint]:
    return _points_from_predictions(_predict_patches(path))
```

对每个 patch：算出时间戳，把效价、唤醒度从 DEAM 的分制换算到项目的范围，组成一个 `EmotionPoint`。

这种方式节省了大量计算。按滑动窗口的做法，模型要调用上千次。用 29 分钟的《Art of Life》实测，得到 1168 个点，含解码在内一共只花费 16 秒。能看到弧线有起伏：开头 15 秒的管弦乐前奏，唤醒度平均 0.35；580 到 620 秒的一个过渡段附近，平均 0.73，接近前奏的 2 倍；全曲最低 0.27，最高 0.84。

### 量表换算

```python
DEAM_SCALE_MIN = 1.0
DEAM_SCALE_MAX = 9.0


def _rescale(value: float, target_min: float, target_max: float) -> float:
    fraction = (value - DEAM_SCALE_MIN) / (DEAM_SCALE_MAX - DEAM_SCALE_MIN)
    return target_min + fraction * (target_max - target_min)
```

这就是第 2.8.3 节的线性换算公式，分两步：先算出这个数在 1 到 9 之间走了百分之多少（`fraction`），再在目标区间里走同样的百分比。效价换算到 -1 到 1，唤醒度换算到 0 到 1，这是项目契约里约定的范围。

`sample.mp3` 的 19 个 patch，原始效价平均 3.73，换算后是 $-1 + \frac{3.73 - 1}{8} \times 2 \approx -0.32$；原始唤醒度平均 3.44，换算后是 $\frac{3.44 - 1}{8} \approx 0.30$。

### 整曲效价与唤醒度

```python
def average_emotion(arc: list[EmotionPoint]) -> tuple[float, float]:
    """Clip-level (valence, arousal) as the arc's mean — exact, not an
    approximation, since rescaling is linear and commutes with averaging."""
    valence = sum(point.valence for point in arc) / len(arc)
    arousal = sum(point.arousal for point in arc) / len(arc)
    return valence, arousal
```

整首歌的效价和唤醒度，就是弧线上所有点的平均值。

这里有一个问题：模型原本的做法是"先对原始分数取平均，再换算"，现在是"先换算每个点，再取平均"，两者结果一样吗？第 2.8.3 节推导过：换算是线性的，线性换算和取平均可以交换顺序，所以两者完全相等。

这个性质让接口只需要调用一次模型：`/internal/classify` 只调用 `model_emotion_arc` 得到弧线，再用 `average_emotion` 算出整首歌的效价和唤醒度。

> 文件里还保留了一个 `classify_emotion` 函数，内部就是 `average_emotion(model_emotion_arc(path))`，给命令行单独测试用，`/internal/classify` 不调用它。

### 情绪标签

```python
QUADRANT_LABELS = {
    (True, True): ["excited", "joyful"],
    (True, False): ["calm", "peaceful"],
    (False, True): ["tense", "anxious"],
    (False, False): ["wistful", "melancholic"],
}


def emotion_labels(valence: float, arousal: float) -> list[str]:
    return QUADRANT_LABELS[(valence >= 0, arousal >= 0.5)]
```

字典的键是两个布尔值：效价是否大于等于 0，唤醒度是否大于等于 0.5。两个布尔值组合出四种情况，正好对应效价-唤醒平面的四个象限，每个象限两个标签：

| | 唤醒度 ≥ 0.5 | 唤醒度 < 0.5 |
|---|---|---|
| 效价 ≥ 0 | excited、joyful（兴奋、喜悦） | calm、peaceful（平静、安宁） |
| 效价 < 0 | tense、anxious（紧张、不安） | wistful、melancholic（惆怅、忧郁） |

命名参照 Thayer 的音乐情绪四象限，但做了调整（第 2.8.3 节）。

`sample.mp3` 效价 -0.32、唤醒度 0.30，落在左下象限，标签是 `wistful`、`melancholic`，和这首咏叹调沉静、略带哀伤的听感一致。

### 在 PMEmo 上验证模型

DEAM 回归头的官方指标是效价 r = 0.738、唤醒度 r = 0.773（r 是 Pearson 相关系数，第 2.7.6 节）。这是在 DEAM 自己的测试集上测的。项目的验证数据来自另一个数据集 PMEmo：另一批歌、另一批标注者，评分习惯也可能不同。官方分数不能直接当作项目的验收结果，必须在自己的数据上重新测（第 2.7.6 节）。

下表列出模型在 PMEmo 上的验证结果，并附上早期谱熵相关性检验的结果作为参考。

| | 项目门槛 | DEAM 官方 | PMEmo 模型实测 | L1 谱熵与人工标注 |
|---|---|---|---|---|
| 效价 | r > 0.4 | 0.738 | **0.67** | 0.553 |
| 唤醒度 | r > 0.4 | 0.773 | **0.52** | 0.486 |

谱熵检验中，每首歌对应三个数，分别是 L1 算出的整曲谱熵、人工标注的效价和人工标注的唤醒度（第 3.6 节）。把这三项数据排成三列，每行对应一首歌。

- **0.553** 是谱熵这一列与人工效价这一列的 Pearson 相关系数。
- **0.486** 是谱熵这一列与人工唤醒度这一列的 Pearson 相关系数。

以效价为例，计算时先让谱熵和效价各自减去本列的平均值，再衡量这些差值是否倾向于同向变化（第 2.7.6 节）。两个相关系数都是正的，说明在这批歌里，谱熵高于平均值的歌曲，两项人工评分也倾向于高于各自的平均值。

模型验证用模型预测值与人工评分计算相关系数，效价和唤醒度均达到了项目设定的门槛。两次检验使用的 PMEmo 曲目范围不同，谱熵一列只作为早期检验的参考。

因为直接推理已经达标，项目原本准备的"自己训练一个情感模型"的备选方案没有执行。

### PMEmo 数据集的构建

验证用的数据集由 `apps/engine/dataset/` 构建，输出一个 CSV 文件，每一行是音频路径、效价、唤醒度、所属的集合：

1. **读取标注**（`pmemo/load.py`）：按静态情感标注逐行读取效价和唤醒度，再匹配对应的音频路径
2. **换算**（`pmemo/common.py`）：PMEmo 的效价标注是 0 到 1，换算成项目的 -1 到 1，公式是 $v \times 2 - 1$；唤醒度本来就是 0 到 1，不需要换算
3. **按时长过滤**（`curate.py`）：去掉短于 5 秒或长于 600 秒的音频。时长用 `soundfile.info` 读文件头，不解码整个文件
4. **切分**（`curate.py`）：按 8:1:1 切分成训练、验证、测试集，随机种子固定，保证每次切分结果一样
5. **写文件**：路径写成绝对路径，在任何工作目录下读这份 CSV 都能找到文件

数据集是为当初"自己训练情感模型"的计划准备的。`pmemo/` 单独成一个子目录，是为以后加入其他数据集（比如 DEAM）留位置；`curate.py` 里的过滤和切分与具体数据集无关，可以复用。

## 4.3 乐器识别:多标签分类

### 乐器识别的任务

这首歌里有哪些乐器？和流派、情感不同，一首歌可以同时有钢琴、鼓和吉他，也可以一件都识别不出来。这是一个多标签问题：每种乐器各自独立判断"有没有"（第 2.7.2 节）。

### 乐器多标签分类模型

乐器识别复用流派识别的 discogs-effnet 骨干（第 4.1 节的共享单例），换一个任务头 `mtg_jamendo_instrument`。这个头在 MTG-Jamendo 数据集上训练，对每种乐器输出一个 0 到 1 之间的 sigmoid 概率，各种乐器之间互不影响，加起来也不等于 1。

40 种乐器包括常见的 piano、drums、bass、guitar、electricguitar、violin、cello、synthesizer，也有 accordion、harmonica、pipeorgan 这类不常见的，还有一个 voice（人声）。

### 乐器得分的分段汇总

```python
SEGMENT_DURATION_SEC = 30
MIN_SEGMENT_DURATION_SEC = 15


def classify_instruments(path: str) -> list[InstrumentEntry]:
    embedding_model, head_model, classes = _load_models()
    audio = es.MonoLoader(filename=path, sampleRate=SAMPLE_RATE, resampleQuality=4)()

    max_scores = {name: 0.0 for name in classes}
    for segment in _split_into_segments(audio):
        embeddings = embedding_model(segment)
        predictions = head_model(embeddings).mean(axis=0)
        for name, score in zip(classes, predictions.tolist()):
            max_scores[name] = max(max_scores[name], score)

    ranked = sorted(max_scores.items(), key=lambda pair: -pair[1])
    return [InstrumentEntry(name=name, confidence=confidence) for name, confidence in ranked if confidence >= CONFIDENCE_THRESHOLD]
```

流程是：

1. 把整首歌切成 30 秒一段（`_split_into_segments`，见下文）
2. 每一段单独过骨干和任务头，**段内**对所有 patch 取平均，得到这一段每种乐器的分数
3. **段与段之间**，每种乐器只保留最高的那一段的分数，存在 `max_scores` 里
4. 按分数从高到低排序，只输出超过阈值 0.35 的乐器

最初的实现和流派一样，对整首歌所有 patch 取一次平均。问题出在 29 分钟的《Art of Life》上：结果是一个空列表。这首歌横跨管弦乐前奏、钢琴、重摇滚好几种编曲，没有一件乐器从头响到尾。整首平均后，鼓 0.32、钢琴 0.32、吉他 0.28，全部低于阈值，被过滤掉了。

根本原因是两个问题的问法不同。流派问"整首歌总体上像什么"，适合平均；乐器问"有没有出现过"，一件只在副歌出现的乐器，不应该因为歌曲其他部分没有它就被平均掉（第 2.7.3 节）。所以改成段内平均、段间取最大值。注意段与段之间不能再取一次平均。

### 音频分段规则

```python
def _split_into_segments(audio: np.ndarray) -> list[np.ndarray]:
    segment_samples = SEGMENT_DURATION_SEC * SAMPLE_RATE
    min_samples = MIN_SEGMENT_DURATION_SEC * SAMPLE_RATE
    total = len(audio)
    if total <= segment_samples:
        return [audio]

    segments = []
    start = 0
    while start < total:
        end = min(start + segment_samples, total)
        if total - end < min_samples:
            end = total  # absorb a short trailing remainder into this segment
        segments.append(audio[start:end])
        start = end
    return segments
```

- 不超过 30 秒的音频，整段作为一段，不切。`sample.mp3` 正好 30 秒，所以只有一段，结果和整首平均完全一样
- 更长的音频，从头开始每 30 秒切一刀
- 切下一刀之前，先看剩下的部分还有多长。如果不到 15 秒，就不再单独成段，而是并入当前这一段。太短的片段 patch 数太少，平均值不稳定

比如一首 100 秒的歌，会切成 0–30、30–60、60–100 三段：切到 60 秒时，剩下 40 秒；如果在 90 秒再切一刀，只剩 10 秒，不到 15 秒，所以并入，最后一段是 40 秒。

### 分段时长的选择

项目从 MTG-Jamendo 选取标签明确的单乐器片段，拼接成乐器出现位置已知的测试音频。对照整曲平均、60 秒分段和 30 秒分段三种方案，比较各乐器的分数及其是否达到识别阈值。

| | 整首平均 | 60 秒分段 | 30 秒分段 |
|---|---|---|---|
| 鼓 | 0.26 | 0.53 | 0.72 |
| 钢琴 | 0.22 | 0.40 | 0.55 |
| 贝斯 | 0.22 | 0.46 | 0.62 |
| 吉他 | 0.15 | 0.24（未过阈值） | **0.40（过阈值）** |
| 小提琴 | 0.10 | 0.20 | 0.33（接近阈值，未过） |
| 小号、单簧管、竖琴、圆号、中提琴、管风琴 | 全部低于 0.09 | 全部低于 0.17 | 全部低于 0.11 |

两个结论：

- **分段有效，30 秒比 60 秒更好。** 常见乐器的分数全面提高，吉他因此跨过了阈值，所以分段长度定为 30 秒。代价是耗时增加：《Art of Life》从 19 秒变成 35 秒。

- **部分乐器的识别得分仍然偏低。** 在单独演奏、边界对齐的测试片段中，小号和单簧管的得分也很低，调整分段长度后变化很小。

采用 30 秒分段后，模型为《Art of Life》输出了 7 个乐器标签，分别是钢琴 0.87、鼓 0.76、吉他 0.66、电吉他 0.49、贝斯 0.46、合成器 0.46 和双簧管 0.39。

对照 X JAPAN 1993 年录音室版的演奏署名，Yoshiki 演奏鼓、钢琴和合成器，hide 和 Pata 演奏吉他，Heath 演奏贝斯，皇家爱乐乐团参与了管弦乐录制。

模型输出的钢琴、鼓、吉他、电吉他、贝斯和合成器都与录音中的乐器相符。「吉他」和「电吉他」是范围有重叠的标签。管弦乐部分有弦乐编排，但模型的弦乐和小提琴标签均未达到阈值。演奏署名没有细列乐团的各件乐器，因此双簧管这一项无法确认。

> 后来用以弦乐编排出名的《Tears》复测，小提琴（0.37）跨过了阈值。说明这个模型对管弦乐器并非没有能力，而是受信噪比、持续时长和混音遮蔽影响。

### 识别阈值 0.35 的选择依据

```python
# Multi-label sigmoid confidence, independent per instrument. False positives
# cost more than misses here (a wrong tag can get cited as evidence by L4),
# so the threshold favors precision.
CONFIDENCE_THRESHOLD = 0.35
```

用 MTG-Jamendo 的标注曲目做了阈值的量化评估。乐器是多标签问题，评估的是"预测出来的乐器集合"和"真实标签集合"有多少重合，用精确率、召回率、F1 衡量（第 2.7.6 节），按每首歌分别计算再取平均。扫描不同阈值：

| 阈值 | 精确率 | 召回率 | F1 |
|---|---|---|---|
| 0.15 | 0.39 | 0.70 | 0.50 |
| 0.25 | 0.48 | 0.56 | 0.52（最高） |
| **0.35** | **0.51** | **0.42** | 0.46 |
| 0.45 | 0.52 | 0.31 | 0.39 |
| 0.55 | 0.51 | 0.23 | 0.32 |
| 0.65 | 0.48 | 0.17 | 0.25 |

如果只看 F1，应该选 0.25。项目选了 0.35，原因是这个产品对两种错误的容忍度不一样：误报的代价更大，所以阈值往精确率的方向调。0.35 是精确率第一次超过召回率的位置；继续提高到 0.45，精确率几乎不再上升（停在 0.51 到 0.52），召回率却大幅下降。0.35 是"转向精确率优先"的临界平衡点。


## 4.4 结构分段:Foote 边界检测与层次聚类

### 边界检测与段落命名

这首歌分成哪几段，每一段是前奏、主歌、副歌、桥段还是尾奏？输出是一个列表，每一项是一个段落的起止时间和类型。

结构分段分两步，用的方法完全不同：

1. **找边界**：段落之间的分界线在哪里。用 MSAF 库的 Foote 算法（第 2.6.3 节）
2. **贴标签**：每一段是什么类型。用项目自己写的聚类加规则

### 边界检测算法的选择

MSAF 是一个音乐结构分析的工具库，内置了 7 种边界检测算法。要比较它们，需要有人工标注了真实边界的数据。MSAF 官方的评测数据里，大部分子集只有标注、没有音频（版权限制），项目选用同时提供完整曲目和人工段落边界的 Sargon 子集。

项目在相同曲目和容差设置下比较了这 7 种算法。指标是边界检测的 F 值（第 2.7.6 节）：预测的边界落在真实边界前后 3 秒内，就算命中。

| 算法 | F 值（3 秒容差） |
|---|---|
| **foote** | **0.733** |
| olda | 0.657 |
| sf | 0.557 |
| cnmf | 0.482 |
| scluster（MSAF 默认） | 0.380 |
| cbm | 0.320 |
| vmo | 0.090 |

Foote 的平均 F 值最高，逐曲结果也较为接近。它是 2000 年提出的经典方法，没有深度学习依赖，被选为主算法。

> MSAF 在 PyPI 上的发布版用了新版 scipy 已经删除的接口，装不上。它的 GitHub 主分支已经修复了这个问题，所以项目从 GitHub 安装，并锁定在一个验证过的提交版本上。

### Foote 边界检测流程

MSAF 的 Foote 实现，内部步骤和第 2.6.3 节讲的一致：

1. **计算特征**：先用谐波/打击乐分离（HPSS）去掉鼓声，再用 CQT 算 chroma（第 2.4.2 节），最后按拍子对齐，每一拍一个 12 维的音级向量
2. **中值滤波**：沿时间方向对特征做中值滤波，去掉零星的杂音（第 2.5.2 节）
3. **自相似矩阵**：用标准化欧氏距离计算每两拍之间的相似度（第 2.6.3 节）
4. **新颖度曲线**：用高斯形状的棋盘核沿对角线滑动（第 2.5.1 节、第 2.6.3 节）
5. **找峰**：先做高斯平滑（第 2.5.2 节），再用"中值滤波得到的局部基线 + 偏移量"作为阈值，找出所有峰（第 2.5.3 节）。每个峰的位置换算成秒，就是一条边界

### 按曲目时长调整参数

Foote 有三个控制时间尺度的参数：

- `M_gaussian = 66`：棋盘核的边长，决定比较"前后多长一段"
- `m_median = 12`：中值滤波的窗口大小
- `L_peaks = 64`：找峰时计算局部基线的窗口大小

关键在于，这三个参数的单位都是**帧**（这里一帧就是一拍），不是秒。它们的默认值是在 Sargon 那批曲目（平均约 400 秒）上调好的。放到其他时长的曲目上，它们代表的帧数不变，但这些帧数在整首歌里占的比例变了。

项目测试了两种极端时长：

- **30 秒的短片段**：默认参数效果很好，切出 3 到 5 段。
- **29 分钟的《Art of Life》**：默认参数切出 114 段，平均每段 15 秒。这首歌是一部由管弦乐、钢琴、重摇滚、抒情段落组成的多段体作品，114 段显然切得太细了

修法是按时长线性放大这三个参数：

```python
REFERENCE_DURATION_SEC = 400
DEFAULT_M_GAUSSIAN = 66
DEFAULT_M_MEDIAN = 12
DEFAULT_L_PEAKS = 64


def _scaled_config(duration_sec: float) -> dict:
    config = msaf_io.get_configuration("pcp", False, False, "foote", None)
    scale = max(1.0, duration_sec / REFERENCE_DURATION_SEC)
    config["M_gaussian"] = round(DEFAULT_M_GAUSSIAN * scale)
    config["m_median"] = round(DEFAULT_M_MEDIAN * scale)
    config["L_peaks"] = round(DEFAULT_L_PEAKS * scale)
    return config
```

逐行看：

1. `get_configuration("pcp", ..., "foote", ...)`：取出 Foote 算法的默认配置，特征类型是 PCP，也就是上面说的 CQT chroma
2. `duration_sec / 400`：以 400 秒为基准
3. `max(1.0, ...)`：短于 400 秒的曲目，`scale` 都是 1，沿用默认参数
4. 三个参数都乘以 `scale`，再四舍五入成整数

《Art of Life》约 1741 秒，`scale` 约为 4.35，`M_gaussian` 从 66 变成 287。放大后切出 30 段左右，符合这首歌的结构粒度。

### 边界检测的实现细节

#### 合并过短的末段

按拍子对齐的边界检测，经常在曲目真正结束前切一刀，产生一个几十毫秒的末尾段。代码规定末尾段短于 1 秒时，直接并入前一段：

```python
MIN_FINAL_SEGMENT_SEC = 1.0

if len(boundaries) > 2 and boundaries[-1] - boundaries[-2] < MIN_FINAL_SEGMENT_SEC:
    boundaries = np.concatenate([boundaries[:-2], boundaries[-1:]])
```

#### MSAF 的临时文件

MSAF 默认把特征缓存写到固定路径，并按音频路径推导结果文件的目录。为减少并发请求共用文件的风险，项目为每次调用创建临时目录，将缓存和结果文件的路径都指向这里。

```python
def _detect_boundaries(path: str, duration_sec: float) -> np.ndarray:
    with tempfile.TemporaryDirectory() as tmp_dir:
        msaf.config.features_tmp_file = os.path.join(tmp_dir, "features.json")
        msaf.config.dataset.estimations_dir = tmp_dir
        boundaries, _ = msaf.run.process(path, boundaries_id="foote", labels_id=None, n_jobs=1, config=_scaled_config(duration_sec))
    return boundaries
```

调用结束后，临时目录自动删除，重复分析同一首歌需要重新计算。目录路径通过 MSAF 的进程级配置设置，多个请求同时运行时仍可能覆盖彼此的配置。以《Art of Life》为例，重新检测边界约需 150 到 215 秒，命中缓存时约需 1.3 秒。

### 段落命名方法的选择

MSAF 有自己的段落标签算法 fmc2d。在 29 分钟的曲目上实测，跑了 14 分钟还没有结束，无法用于生产。所以只让 MSAF 找边界，标签由项目自己计算，分三步：

1. 给每个段落算一个特征向量
2. 用层次聚类把相似的段落分到同一组
3. 按规则把组号翻译成段落名称

### 第一步:提取段落特征

```python
CHROMA_N_FFT = 2048
CHROMA_HOP_LENGTH = 512


def _segment_feature_vectors(y: np.ndarray, boundaries: np.ndarray) -> np.ndarray:
    chroma_vectors = []
    energy_scalars = []
    placeholder_indices = []
    for i, (start_sec, end_sec) in enumerate(pairwise(boundaries)):
        start = int(start_sec * SAMPLE_RATE)
        end = int(end_sec * SAMPLE_RATE)
        if end - start < SAMPLE_RATE:
            # Too short for a meaningful estimate of either feature.
            chroma_vectors.append(np.full(12, 1 / 12))
            energy_scalars.append(0.0)
            placeholder_indices.append(i)
            continue
        segment = y[start:end]
        chroma = librosa.feature.chroma_stft(y=segment, sr=SAMPLE_RATE, n_fft=CHROMA_N_FFT, hop_length=CHROMA_HOP_LENGTH)
        chroma_vectors.append(chroma.mean(axis=1))
        energy_scalars.append(float(librosa.feature.rms(y=segment, hop_length=CHROMA_HOP_LENGTH)[0].mean()))
    # ... 归一化后拼接，见下文
```

这里的 `y` 是 `segment_structure` 用 librosa 解码的 22050 Hz 单声道波形。`pairwise(boundaries)` 把边界数组两两配对：边界是 `[0, 1.8, 30]`，配对后就是 `(0, 1.8)`、`(1.8, 30)` 两段。

对每个段落：

- 把起止时间换成采样点下标，切出这一段的波形
- 算这一段的 chroma（第 2.4.2 节），对时间取平均，得到 12 个数，表示这一段整体上各个音级有多强
- 算这一段的 RMS（第 2.2.3 节），对时间取平均，得到 1 个数，表示这一段整体有多响

#### 响度在段落区分中的作用

第一版只用了 chroma。用《Wonderwall》《Californication》这类和声单一的流行歌测试，前奏之后的所有段落都被判成了副歌，主歌完全消失。原因是西方流行歌的主歌和副歌，往往用同一个调、同一组和弦，chroma 几乎没有区别，全部聚成一组，又被"出现最多的一组是副歌"这条规则整体判成副歌。主歌和副歌在和声相同时，最稳定的区别是响度：副歌通常更响、编曲更满。所以加上了响度这一维。

#### chroma 与响度的缩放和拼接

12 维的 chroma 和 1 维的响度尺度不同，不能直接拼（第 2.9.2 节）：

```python
    chroma_matrix = np.array(chroma_vectors)
    chroma_norms = np.linalg.norm(chroma_matrix, axis=1, keepdims=True)
    chroma_matrix = chroma_matrix / np.where(chroma_norms < 1e-9, 1.0, chroma_norms)

    # ... 占位段落的处理，见下文

    energy_std = energy_vector.std()
    energy_z = (energy_vector - energy_vector.mean()) / (energy_std if energy_std > 1e-9 else 1.0)

    return np.column_stack([chroma_matrix, energy_z])
```

- **chroma 归一化。** 将 chroma 除以自身长度，变成单位向量，只比较各个音级之间的比例。`np.where(chroma_norms < 1e-9, 1.0, chroma_norms)` 的意思是：如果某一段的 chroma 全是 0（完全无声），长度是 0，就改成除以 1，避免除以 0。
- **响度标准化。** 用 z-score 处理，即减去本曲所有段落的平均响度，再除以标准差。结果表示"这一段比本曲的平均响度高几个标准差"。和本曲自己比，而不是和一个固定标准比，所以整首歌音量大小不影响结果。如果所有段落响度完全相同，标准差是 0，同样改成除以 1。
- **拼接特征。** `np.column_stack` 把两部分左右拼起来，每个段落得到一个 13 维的向量。

### 过短段落的占位值

聚类需要每个段落都有一组特征。对于短于 1 秒的段落，代码跳过 chroma 和 RMS 的计算，先给 12 个音级都填上 $1/12$，把平均 RMS 暂记为 0，并记录这个段落的编号。

如果拿这个 0 直接去聚类，过短的段落就可能被当作特别安静的一段，甚至单独分到一组。因此，在做 z-score 之前，代码用其他段落的平均 RMS 替换这个 0。

```python
    energy_vector = np.array(energy_scalars)
    if placeholder_indices and len(placeholder_indices) < len(energy_vector):
        real_mask = np.ones(len(energy_vector), dtype=bool)
        real_mask[placeholder_indices] = False
        energy_vector[placeholder_indices] = energy_vector[real_mask].mean()
```

例如，两个正常段落的平均 RMS 分别是 0.08 和 0.12，第三段太短，暂记为 0。代码用 `real_mask` 选出前两段，算出平均值 0.10，再填到第三段。这样三个值就成了 `[0.08, 0.12, 0.10]`，平均值仍是 0.10。第三段做 z-score 时，$0.10 - 0.10 = 0$，所以它在响度这一维上处于平均水平。

回填平均值只决定第三段在响度这一维上的取值。分组时还要把 12 维 chroma 一起算进距离。回填至少需要一个实际计算了 RMS 的段落。如果所有段落都太短，代码就保留原来的占位值。

### 第二步:层次聚类

```python
CLUSTER_DISTANCE_THRESHOLD = 0.5


def _cluster_ids(vectors: np.ndarray) -> list[int]:
    if len(vectors) < 2:
        return [0] * len(vectors)
    distances = pdist(vectors, metric="euclidean")
    linkage_matrix = linkage(distances, method="average")
    return fcluster(linkage_matrix, t=CLUSTER_DISTANCE_THRESHOLD, criterion="distance").tolist()
```

这是第 2.7.4 节讲过的三步：`pdist` 算出所有段落两两之间的欧氏距离，`linkage` 用 average 准则自底向上地合并，`fcluster` 在距离 0.5 的高度横切树状图，得到每个段落的组号。只有一个段落时，没有东西可以比较，直接返回组号 0。

用距离阈值而不是"分成 k 组"，是因为事先不知道一首歌有几种段落（第 2.7.4 节）。

项目在测试组中扫描距离阈值，并观察分组结果。

- 阈值更低：大部分段落各成一组，又因为"只出现一次"被判成桥段，结构碎成一片
- 阈值更高：所有段落合并成少数几组，最后又退化成"几乎全是副歌"

### 第三步:根据分组命名段落

```python
def _map_segment_types(cluster_ids: list[int]) -> list[str]:
    counts = Counter(cluster_ids)
    most_common_id, _ = counts.most_common(1)[0]
    last_index = len(cluster_ids) - 1
    types = []
    for i, cluster_id in enumerate(cluster_ids):
        if i == 0:
            types.append("intro")
        elif counts[cluster_id] == 1:
            types.append("outro" if i == last_index else "bridge")
        elif cluster_id == most_common_id:
            types.append("chorus")
        else:
            types.append("verse")
    return types
```

`Counter` 统计每个组出现了几次，`most_common(1)` 找出出现次数最多的组。然后对每个段落按顺序判断，命中一条就不再往下看：

1. 第一段是前奏（intro）
2. 这一段所在的组只出现过一次：如果它是最后一段，是尾奏（outro）；否则是桥段（bridge）
3. 这一段属于出现次数最多的组：副歌（chorus）
4. 其余是主歌（verse）

举个例子。假设一首歌切成 7 段，聚类后的组号是 `[1, 2, 3, 2, 3, 4, 3]`。组 3 出现 3 次，最多；组 1 和组 4 各出现 1 次。按规则：

| 段落 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|---|---|
| 组号 | 1 | 2 | 3 | 2 | 3 | 4 | 3 |
| 类型 | intro | verse | chorus | verse | chorus | bridge | chorus |

这正是流行歌最常见的"前奏—主歌—副歌—主歌—副歌—桥段—副歌"结构。

### 已知局限

- **响度可能主导距离。** 归一化后的非负 chroma 向量之间的距离最多为 $\sqrt{2}$。响度直接以 z-score 的差值计入距离。例如，两段的 chroma 完全相同时，若平均 RMS 相差超过本曲段落 RMS 标准差的 0.5 倍，这两个特征向量的距离就超过了聚类阈值 0.5。该阈值根据测试组的结果选定，没有专门验证动态范围特别大的曲目。
- **最后一遍副歌升调。** 流行歌常见的做法是最后一遍副歌整体升高半音或全音。升调后 chroma 和前面的副歌对不上，会被单独分成一组；它又恰好是最后一段，会被判成尾奏。

## 4.5 和弦识别:DeepChroma 与 CRF 解码

### 和弦识别的任务

这首歌在每个时刻用的是什么和弦？输出是一串带起止时间的和弦，比如"1.4 到 5.3 秒是 G，5.3 到 6.5 秒是 F#m"。

### 和弦识别工具的选择

调研了三个现成方案：

- **madmom**：用神经网络算 DeepChroma，再用 CRF 解码成和弦序列。PyPI 上的发布版在新版 Python 上装不上，但 GitHub 主分支已经修复了这些问题
- **autochord**：模型是旧版 TensorFlow 格式，新版 TensorFlow 已经不能加载，要精确锁定旧版本才能用
- **Essentia 的 ChordsDetection**：官方文档标注为实验性功能，原理和手写 chroma 模板匹配相同：12 个大三和弦、12 个小三和弦各一个模板，每一帧和 24 个模板比较，取最像的那个

最终选了 madmom，和 MSAF 一样从 GitHub 安装，锁定一个验证过的提交版本。

### 从 DeepChroma 到和弦序列

```python
def recognize_chords(path: str) -> list[ChordEvent]:
    chroma_processor, chord_processor = _load_processors()
    chroma = chroma_processor(path)
    raw_chords = chord_processor(chroma)

    return [
        ChordEvent(start_sec=float(start_sec), end_sec=float(end_sec), chord=chord)
        for start_sec, end_sec, label in raw_chords
        if (chord := _format_label(label)) is not None
    ]
```

这是第 2.7.5 节讲的"神经网络 + 序列解码"两段式结构：

1. **`DeepChromaProcessor`**：神经网络从频谱算出 chroma，每秒 10 帧（第 2.4.2 节）。它接收文件路径，内部会自己解码并重采样到 44100 Hz。和 L1 的 `chroma_stft` 相比，它学会了区分"哪些能量来自泛音、哪些来自鼓、哪些才是真正在响的音"，结果干净得多
2. **`DeepChromaChordRecognitionProcessor`**：CRF 在逐帧的 chroma 上解码，找出最合理的一整条和弦序列（第 2.7.5 节）。相邻帧之间有约束，和弦不会每帧乱跳

CRF 解码的结果不是逐帧的标签，而是带起止时间的区间，相邻相同的和弦已经合并成一段。项目最初计划自己写的两条后处理，"相邻相同的和弦合并"和"持续不到 1 秒的忽略"，CRF 已经处理了，不需要再写。

### 支持的和弦类型

madmom 的和弦模型只有 25 个标签：12 个大三和弦、12 个小三和弦，加上一个 N（无和弦）。这套词表叫 majmin（major 和 minor）。没有减三和弦，没有七和弦（第 2.1.2 节）。遇到一个 G7 和弦，模型只能从这 25 个里选一个输出，通常是 G。

这个限制直接影响了 L3。结构逻辑评分有两处依赖它（第 5.3 节）：

- "和弦种类数"子指标的上限是 24，就是这个词表的大小
- 和声功能清单不收录减三和弦，因为模型永远不会输出它（第 2.1.2 节）

### 和弦事件的输出格式

```python
def _format_label(madmom_label: str) -> str | None:
    if madmom_label == "N":
        return None
    root, quality = madmom_label.split(":")
    return f"{root}m" if quality == "min" else root
```

madmom 的原始输出是 `G:maj`、`F#:min`、`N` 这样的字符串。代码按冒号拆成根音和种类，大三和弦只保留根音（`G`），小三和弦在根音后面加 `m`（`F#m`）。`N` 返回 `None`，在上面的列表推导里被过滤掉。

转换格式不是出于美观。结果页有一个"高亮主和弦"的功能：前端根据调性算出主和弦，比如 G 大调的主和弦是 `G`，D 小调是 `Dm`，然后在和弦列表里用字符串相等找出所有主和弦，标成深紫色。前端算出的格式是 `G`、`Gm` 这样的简写。

> 前端的这个函数也处理了等音异名的问题：调性如果是 `"Bb major"`，它会先把 Bb 换成 A#，因为 madmom 的和弦名只用升号（第 2.1.1 节）。

无和弦的区间直接丢弃，因为和弦列表本来就不需要显示"这里没有和弦"的空白。

`sample.mp3` 的原始输出第一段是 0 到 1.4 秒的 N，被丢掉了；之后是 12 个和弦：

| 时间（秒） | 1.4 | 5.3 | 6.5 | 9.3 | 10.9 | 13.2 | 17.1 | 20.2 | 21.3 | 24.1 | 25.2 | 29.1 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|
| 和弦 | G | F#m | D | Em | C | D | G | F# | Em | D | A | D |

这首曲子被 L1 检测为 G 大调。12 个和弦里，G、D、Em、C 都是 G 大调的核心和弦，L3 算出的和声功能覆盖率是 0.75，完整计算见第 5.3 节。

### 和弦识别的验证范围

和弦识别没有做量化评估：找不到同时提供真实音频和人工和弦标注、又没有版权限制的公开数据集。和弦识别的结果不能当作一定可靠的结论，第 7.1 节把它列为已知局限。

## 4.6 拍号检测:RNN 与 DBN 解码

### 拍号检测的任务

这首歌每小节几拍？拍号的概念见第 2.1.3 节。输出是一个字符串，比如 `"4/4"`，或者带问号的 `"3/4?"`。

### 拍点与强拍的预测和解码

```python
BEATS_PER_BAR_CANDIDATES = [3, 4]


def _load_processors():
    global _activation_processor, _tracking_processor
    if _activation_processor is None:
        _activation_processor = RNNDownBeatProcessor()
        _tracking_processor = DBNDownBeatTrackingProcessor(beats_per_bar=BEATS_PER_BAR_CANDIDATES, fps=100)
    return _activation_processor, _tracking_processor
```

两步结构和和弦识别相同，也是"神经网络 + 序列解码"（第 2.7.5 节）：

1. **`RNNDownBeatProcessor`**：一个循环神经网络，逐帧输出两个概率："这里是一拍"和"这里是强拍"，每秒 100 帧。它同样接收文件路径，自己解码
2. **`DBNDownBeatTrackingProcessor`**：DBN（动态贝叶斯网络，HMM 的推广）在 RNN 的概率之上解码，找出最合理的一串拍点。它的隐藏状态同时包括"当前速度"和"这一拍在小节里是第几拍"。`beats_per_bar=[3, 4]` 告诉它：一个小节只可能是 3 拍或 4 拍

DBN 的输出是一个二维数组，每一行是一拍：第一列是这一拍的时间，第二列是它在小节里是第几拍（1、2、3……，1 就是强拍）。

### 拍数候选与拍号检测的局限

`beats_per_bar` 参数可以传任意的候选列表，比如 `[2, 3, 4, 5, 7]`。项目将候选限制为 3 和 4。理解这一设置需要区分训练数据、拍号的表示方式和解码器的假设。

1. **训练数据**：RNN 的训练数据以西方流行、摇滚、古典为主，几乎没见过 5 拍子、7 拍子的强拍规律
2. **"每小节几拍"和拍号不是一回事**：6/8 拍通常按两个大拍感受（第 2.1.3 节）。项目只估计每小节拍数，并统一用 `N/4` 表示结果，因此无法从输出中区分 6/8 等拍号
3. **DBN 的假设**：DBN 内部假设一个小节里的拍是等距的，而 5/4、7/8 这类拍子通常是 3+2、2+2+3 这样不对称的分组

### 用众数推断每小节拍数

```python
positions = beats[:, 1].astype(int) if beats.ndim == 2 and len(beats) else np.empty(0, dtype=int)
downbeats = np.where(positions == 1)[0]

bar_lengths = np.diff(downbeats)
counts = np.bincount(bar_lengths)
beats_per_bar = int(counts.argmax())
agreement = counts.max() / len(bar_lengths)
```

逐行看：

1. `beats[:, 1]`：取出每一拍在小节里的位置，比如 `[1, 2, 3, 1, 2, 3, 1, 2, 3, 4, 1, ...]`。前面的条件是防御性的：如果 DBN 一拍都没找到，就得到一个空数组
2. `np.where(positions == 1)[0]`：找出所有强拍是第几拍。上面的例子里是 `[0, 3, 6, 10, ...]`
3. `np.diff(downbeats)`：相邻两个强拍之间隔了几拍，就是每个小节的拍数：`[3, 3, 4, ...]`
4. `np.bincount` 和 `argmax`：统计每种拍数出现了几次，取出现最多的，也就是**众数**（第 2.9.1 节）
5. `agreement`：众数出现的次数占所有小节的比例，表示有多少小节"同意"这个结果

第一版取的是位置的最大值：只要出现过一个位置 4，就判成 4/4。DBN 在一首 3/4 的歌里偶尔解码错一个小节，就会把整首歌翻转成 4/4。改成众数后，个别错误的小节不再影响结果。第 2.9.1 节用一个 10 小节的例子演示过：拍数是 `[4, 4, 4, 3, 4, 4, 4, 4, 2, 4]` 时，众数是 4，同意的比例是 80%。

### 拍号不确定时的问号标记

```python
MODE_AGREEMENT_THRESHOLD = 0.6

suffix = "" if agreement >= MODE_AGREEMENT_THRESHOLD else "?"
return f"{beats_per_bar}/4{suffix}"
```

如果同意众数的小节不到 60%，说明两种拍数比较接近，结果后面加一个问号，比如 `"3/4?"`，表示这只是一个最佳猜测。结果页直接显示这个字符串，问号也会显示出来。

还有一种情况：如果强拍不足两个，就没有完整的小节可以计算。这时代码取位置的最大值作为猜测（如果一拍都没有，就猜 4），同样带上问号：

```python
if len(downbeats) < 2:
    # No complete bar to measure — whatever we report is a guess.
    fallback = int(positions.max()) if len(positions) else BEATS_PER_BAR_CANDIDATES[-1]
    return f"{fallback}/4?"
```

输出固定写成 `N/4` 的形式。这个字段只用于展示和交给 LLM，没有任何代码会解析它，所以不需要更复杂的格式。

### 节拍规整性对检测结果的影响

拍号检测最初用一首三拍子的曲目测试，就判错了：柏辽兹《幻想交响曲》的"舞会"乐章，明确是圆舞曲，结果是 4/4。打印每一拍的时间发现，模型全程稳定地锁定在 4 拍一小节，是很确定地判错了。

测试提示，节拍和强拍的规整程度可能影响检测结果。

在测试组的歌曲里，《哥德堡变奏曲》咏叹调（旋律线条规整的 3/4）判对了，符合这个规律。

这个结论写进了代码注释，也是第 7.1 节列出的已知局限：节拍自由或强拍不明确时，模型可能把三拍子判成四拍子。这些案例用于说明已观察到的误判，其他曲目的准确性仍需验证。

## 4.7 张力与释放:不协和度的均值与峰后回落

### 张力与释放的定义

张力和释放不像 BPM、调性那样有公认的标准算法。"这段音乐很紧张"可以指和声不协和、节奏密集、音量大、旋律在高音区，很多种因素都可能。项目先明确了它们测的物理量：每一帧声音的**感官不协和度**，也就是声音听起来有多粗糙（第 2.8.1 节）。

在这个定义下：

- **张力**：整首歌平均有多不协和
- **释放**：不协和的高峰过去之后，不协和度降下来多少

两者是同一条不协和度曲线的两种读法，不是两个独立的信号。

### 逐帧不协和度的计算

```python
SAMPLE_RATE = 44100
FRAME_SIZE = 2048
HOP_SIZE = 1024


def frame_dissonance(path: str) -> np.ndarray:
    audio = es.MonoLoader(filename=path, sampleRate=SAMPLE_RATE)()
    windowing, spectrum, spectral_peaks, dissonance = _load_algorithms()

    values = []
    for frame in es.FrameGenerator(audio, frameSize=FRAME_SIZE, hopSize=HOP_SIZE, startFromZero=True):
        freqs, mags = spectral_peaks(spectrum(windowing(frame)))
        if len(freqs) == 0:
            continue
        values.append(dissonance(freqs, mags))
    return np.array(values)
```

四个 Essentia 算法在 `_load_algorithms` 里各创建一次。对每一帧，按顺序做四件事：

1. `windowing`：乘以 Hann 窗，减少频谱泄漏（第 2.3.2 节）
2. `spectrum`：算出这一帧的频谱
3. `spectral_peaks`：在频谱上找峰值，返回每个峰的频率和幅度（第 2.3.2 节）
4. `dissonance`：把所有峰两两配对，用 Plomp-Levelt 曲线算出每一对的粗糙度，按幅度加权求和（第 2.8.1 节），结果在 0 到 1 之间，0 是完全协和，1 是完全不协和

帧长 2048，帧移 1024，在 44100 Hz 下每 $1024 / 44100 \approx 23$ 毫秒一个值。没有任何峰值的帧，比如完全无声的帧，直接跳过，不放进曲线。`sample.mp3` 得到 1288 个值，平均 0.40。

### 不协和度计算所需的频谱

L1 已经算好了 mel 频谱，但这里用不上。不协和度要的是每个频谱峰值的**精确频率**：两个峰相差 5 Hz 还是 30 Hz，粗糙度完全不同（第 2.8.1 节的曲线）。mel 频谱把 1025 个频率格点合并成了 128 个频带，高频的一个频带有几百 Hz 宽，精确频率已经丢失了。所以这个模块自己用 44100 Hz 重新解码，在线性频谱上找峰值。

### 张力:整曲不协和度的均值

```python
# Empirical — the most dissonant real track's mean frame dissonance measured
# scored ~0.9.
REFERENCE_MEAN_DISSONANCE = 0.51


def compute_tension(path: str) -> float:
    values = frame_dissonance(path)
    if len(values) == 0:
        return 0.0
    return float(np.clip(values.mean() / REFERENCE_MEAN_DISSONANCE, 0.0, 1.0))
```

整条曲线的平均值，除以参照值 0.51，截断到 0 到 1（第 2.9.4 节）。如果整首歌没有一帧有峰值（完全静音），返回 0。

校准曲目中，《Art of Life》的平均不协和度最高，为 0.460。项目将该观测值对应到约 0.9，得到经验参照值 $0.460 / 0.9 \approx 0.51$。复测中，《Wonderwall》的平均不协和度为 0.463，接近原来的校准观测值。

`sample.mp3` 的平均不协和度是 0.40，$0.40 / 0.51 \approx 0.78$。

**意外的测试结果**

原本以为以频繁转调、和声复杂著称的爵士名曲《Giant Steps》会是不协和度最高的。它的实测均值为 0.445，低于《Art of Life》（0.460）和《Californication》（0.452）两首摇滚、放克曲目。

原因是感官不协和度测的是声学上的粗糙感，不是乐理上的和声复杂度。失真吉他会产生大量不规则的泛音，即使弹的是简单的三和弦，声学上也很粗糙；《Giant Steps》用的是萨克斯、钢琴、贝斯，音色干净，和声虽然复杂，物理上的粗糙感反而不高。所以 `tension` 这个字段应该理解为"声音有多粗糙"，而不是"和声有多紧张"。这也是第 2.8.1 节说的：这个模型测不出听者对和声功能的预期。

另一个观察是区分度不高：校准组的平均不协和度落在 0.34 到 0.46 之间，换算后挤在 0.67 到 0.90。`sample.mp3` 这首安静的咏叹调也有 0.78，说明这个字段在不同歌曲之间拉不开太大差距。

### 释放:不协和度的峰后回落

释放衡量不协和度在峰值之后下降了多少。`release.py` 用 `frame_dissonance` 计算不协和度曲线，再在曲线上找峰。峰的高度与显著性阈值也根据曲线的均值和标准差设定（第 3.10 节）。释放计算要求保留的峰至少相隔约 0.5 秒。

选出峰以后，取每个峰之后 1.5 秒的数据来计算回落。例如，某个峰的不协和度是 0.60，之后 1.5 秒的平均值是 0.40，这次回落就是 $0.60 - 0.40 = 0.20$。曲目快结束时，如果峰后凑不满 1.5 秒，就跳过这个峰。

把所有回落值取平均，再除以参照值 0.147，将结果限制在 0 到 1。没有可用的峰时，返回 0。参照值以校准曲目《Poesía》的平均回落约 0.132 为依据，按 $0.132 / 0.9 \approx 0.147$ 设定。

```python
FRAME_SEC = HOP_SIZE / SAMPLE_RATE

HEIGHT_STD_MULTIPLIER = 0.5
PROMINENCE_STD_MULTIPLIER = 0.5
MIN_PEAK_GAP_SEC = 0.5
RESOLUTION_WINDOW_SEC = 1.5
REFERENCE_MEAN_DROP = 0.147


def compute_release(path: str) -> float:
    dissonance = frame_dissonance(path)
    if len(dissonance) == 0:
        return 0.0

    height = dissonance.mean() + HEIGHT_STD_MULTIPLIER * dissonance.std()
    prominence = PROMINENCE_STD_MULTIPLIER * dissonance.std()
    min_gap_frames = max(1, round(MIN_PEAK_GAP_SEC / FRAME_SEC))
    peaks, _ = scipy.signal.find_peaks(dissonance, height=height, prominence=prominence, distance=min_gap_frames)

    window_frames = max(1, round(RESOLUTION_WINDOW_SEC / FRAME_SEC))
    drops = [dissonance[i] - dissonance[i + 1 : i + 1 + window_frames].mean() for i in peaks if i + 1 + window_frames <= len(dissonance)]
    if not drops:
        return 0.0
    return float(np.clip(np.mean(drops) / REFERENCE_MEAN_DROP, 0.0, 1.0))
```

`sample.mp3` 的释放得分是 0.49。

### 张力与释放的测试结果

在测试组的歌曲里，释放感最强的是独奏钢琴和古典曲目：《Poesía》、《哥德堡变奏曲》、《G 弦上的咏叹调》。释放感最弱的是失真音色主导的摇滚：《Wonderwall》、《Art of Life》、《Californication》。

在这些测试曲目中，持续的失真音色可能让不协和度保持在较高水平，峰值后的平均回落较小。部分独奏曲目的峰后回落更明显。这项指标依据声学曲线计算，是否出现了乐理上的和声解决还要结合具体和弦判断。

## 4.8 能量感:响度与起音爆发密度

### 能量感的含义

这首歌听起来有没有能量、有没有冲击力？

### 能量感的计算

能量感的设计参考了 Spotify 对 `energy` 的定义。它描述音乐听起来有多强烈、多活跃，影响因素包括感知响度、起音频率和音色等。

本项目用响度和起音爆发密度来衡量能量感。两项分别除以依据校准曲目设定的参照值，将结果限制在 0 到 1，再各按 50% 加权。

- **响度。** 取逐帧 RMS 的第 90 百分位数，用它代表曲目中较响部分的幅度。这个值比最大值更少受个别尖峰影响（第 2.9.1 节）。校准曲目《Californication》的第 90 百分位数为 0.452。项目将该观测值对应到约 0.9，得到参照值约为 0.50。
- **起音爆发密度。** 统计平均每分钟有多少个起音强度峰通过筛选（第 3.10 节）。这一项与 L3 的活力张力共用计算函数和参照值 310。这个参照值根据《Forever Love》约每分钟 279 个峰的观测结果设定（第 3.10 节）。

```python
LOUDNESS_PERCENTILE = 90
LOUDNESS_REFERENCE = 0.50  # empirical — the loudest real track measured scored ~0.9
WEIGHTS = {"loudness": 0.5, "burst_density": 0.5}


def compute_energy(fb: FeatureBundle) -> float:
    loudness = float(np.percentile(fb.rms, LOUDNESS_PERCENTILE))
    loudness_score = np.clip(loudness / LOUDNESS_REFERENCE, 0.0, 1.0)

    burst_density = onset_burst_density(fb.onset_strength, fb.sample_rate, fb.duration_sec)
    burst_score = np.clip(burst_density / BURST_DENSITY_REFERENCE_PER_MIN, 0.0, 1.0)

    return float(loudness_score * WEIGHTS["loudness"] + burst_score * WEIGHTS["burst_density"])
```

### sample.mp3 的计算示例

以 `sample.mp3` 为例，RMS 的第 90 百分位数约为 0.042，换算后为 $0.042 / 0.50 = 0.084$。每分钟有 216 个起音强度峰，换算后为 $216 / 310 \approx 0.70$。两项各占一半，能量感约为 0.39。这段咏叹调的幅度较低，起音较密，因此起音爆发密度贡献了大部分得分。

### 复用 L1 的 RMS 与起音强度

`compute_energy` 接收 `FeatureBundle`，直接使用其中的 RMS 和起音强度。

## 4.9 本章小结

L2 将音频转换为可供后续分析的音乐信息。流派、乐器和情感使用预训练模型，和弦与拍号结合模型输出和序列解码，段落结构则通过边界检测、聚类和命名规则得到。张力、释放和能量感依据不协和度、RMS 与起音强度等信号特征计算。

各项输出都有明确的适用范围。例如，乐器识别通过分段汇总保留只在部分段落出现的乐器信号，拍号检测主要在每小节三拍和四拍之间作出判断。下一章将使用和弦、段落和情感弧线等结果计算评分，这些结果的误差也会影响相应的子指标。
