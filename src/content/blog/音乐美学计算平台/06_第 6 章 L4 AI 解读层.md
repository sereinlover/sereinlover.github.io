# 第 6 章 L4:AI 解读层

L1 到 L3 计算得出几十个数字：BPM、调性、动态范围、四个维度的分数和证据。这些数字对用户来说很难读懂。L4 要做的，是把它们翻译成用户能读懂的文字，也就是第 1.3 节引用的那段《Forever Love》的 AI 解读。

这一层是整个项目里唯一调用大模型的地方。大模型擅长写通顺的文字，也容易编造数字、读错含义（第 2.10.1 节）。L4 的设计就是围绕这一点展开的：让大模型发挥写作能力，同时用代码约束它，让它的输出可以被检查、被追溯。

## L4 的接口与代码结构

### 解读接口与追问接口

L4 对外有两个接口，实现在 `routers/harness.py`：

| 接口 | 作用 | 什么时候调用 | 实现 |
|---|---|---|---|
| `/internal/explain` | 生成整首歌的 AI 解读 | Gateway 处理一首歌的最后一步 | `orchestrator.py: run_explain` |
| `/internal/chat` | 回答用户的追问 | 用户在结果页提问时 | `orchestrator.py: run_chat` |

和 L1 到 L3 的接口一样，这两个接口只接受带有内部密钥的请求：请求头里必须带上 `X-Internal-Token`，值和 Engine 环境变量 `INTERNAL_TOKEN` 一致，否则返回 401。

### 输入:L1 到 L3 的分析结果

`/internal/explain` 的请求体里，除了 `audio_id`、语言等信息，最重要的是三份数据：

- `feature_summary`：L1 的标量特征，比如 BPM、调性、动态范围（第 3.11 节）。
- `understanding`：L2 的全部结果，比如流派、情感弧线、乐器、段落、和弦（第 4 章）。
- `aesthetic`：L3 的四个分数和各自的证据（第 5 章）。

这三份数据都由 Gateway 传进来，是前面三个接口返回的结果。L4 不重新计算任何东西。

### 输出:AnalysisResult 的字段

`/internal/explain` 返回一个 `AnalysisResult`，它就是 Gateway 存进数据库、前端结果页展示的那份完整结果：

| 字段                                            | 含义               | 来自         |
| --------------------------------------------- | ---------------- | ---------- |
| `audio_id`                                    | 文件内容的哈希值         | 请求         |
| `feature_summary`、`understanding`、`aesthetic` | L1 到 L3 的结果，原样返回 | 请求         |
| `summary`                                     | 2 到 3 句总结        | 大模型        |
| `explanation`                                 | 四个维度的详细解读        | 大模型，经过工具提交 |
| `verified`                                    | 四个维度是否都提交了解读     | 代码统计       |
| `tool_call_count`                             | 成功的工具调用次数        | 代码统计       |
| `tool_call_log`                               | 每次成功工具调用的完整记录    | 代码记录       |
| `explanation_skipped`                         | 是否跳过了 L4         | Gateway 设置 |

### L4 的文件与职责

代码在 `apps/engine/harness/` 下：

| 文件                         | 内容                               | 本章小节    |
| -------------------------- | -------------------------------- | ------- |
| `orchestrator.py`          | 生成解读、转换工具 Schema、组装上下文、记录调用与回答追问 | 6.1–6.6 |
| `registry.py`              | 工具注册表：大模型可以调用哪些工具                | 6.3     |
| `tools/explain_dimension/` | 唯一的工具，包括设计文档 `TOOL.md` 和实现       | 6.3     |
| `system_prompt.py`         | 生成解读和回答追问使用的系统提示词                | 6.4、6.6 |

## 6.1 L4 的职责:基于分析结果生成解读

### 大模型的调用位置

整条流水线里，只有 L4 调用大模型。`orchestrator.py` 文件开头的说明：

```python
"""L4 Harness Orchestrator — the one place that calls a real LLM.

Treats L1-L3's outputs (feature_summary/understanding/aesthetic) as
already-computed context and runs a tool-use loop where the model must call
`explain_dimension` once per aesthetic dimension (see
harness/tools/explain_dimension/TOOL.md for why the tool itself doesn't
generate text). `run_explain` produces the initial AnalysisResult; `run_chat`
answers a stateless follow-up question, rebuilding context fresh each call
from what Gateway already has on hand.
"""
```

意思是：L1 到 L3 的结果被当作"已经算好的上下文"交给大模型，大模型在一个循环里为每个维度调用一次 `explain_dimension` 工具；`run_explain` 生成第一份解读，`run_chat` 回答追问，每次都从 Gateway 得到的数据里重新拼出上下文。

### 计算与解读分开的原因

另一种做法是把音频特征直接交给大模型，让它自己判断"这首歌的结构逻辑得几分"。项目没有这样做，原因有三个：

- **大模型算数不可靠。** 第 2.10.1 节讲过，大模型是逐个预测 token 的，数字可能抄错、编造，或者理解错含义。
- **结果不可复现。** 同一首歌问两次，大模型可能给出两个不同的分数。确定性的代码，同样的输入永远得到同样的输出。
- **无法测试。** 第 5 章的每个公式都有单元测试，可以构造一组输入、断言输出等于某个值。大模型的输出没法这样测试。

L4 根据 L3 给出的分数和证据，解释各维度测到了什么。分数采用项目当前的计分尺度，证据则保留了用于计算的原始指标（第 5.1 节）。例如，动态范围 24.68 dB 描述的是音频中较响与较轻部分的幅度差异。

`system_prompt.py` 的文件头把这个原则写成了三条：

```python
"""
Design principles:
- L1-L3 are done ahead of time by deterministic computation modules; the LLM receives the results as context
- The LLM's only job is calling explain_dimension to produce a natural-language explanation backed by evidence
- Every numeric claim must come from the provided context — the LLM must not infer any of its own
"""
```

1. L1 到 L3 由确定性的计算模块提前完成，大模型拿到的是结果。
2. 大模型唯一的任务，是调用 `explain_dimension`，写出有证据支撑的解释。
3. 每一个数字都必须来自给定的上下文，大模型不能自己推断。

### 未配置 API Key 时跳过解读

如果部署时没有配置大模型的 API Key，Gateway 处理完 L1 到 L3 之后，不会调用 `/internal/explain`，而是直接生成一份 `explanation_skipped` 为真的结果：

```go
if !w.HasOpenAIKey {
    // ...
    return explainSkippedResult(job.AudioID, features, understanding, aesthetic), nil
}
```

这份结果里有 L1 到 L3 的全部数据，`summary` 和 `explanation` 是空的。前端看到 `explanation_skipped` 为真，就在 AI 解读的位置显示"尚未配置 OPENAI_API_KEY，该功能不可用"，进度条上这一步显示"（跳过）"。仍然能看到流派、情感、结构、四个维度分数等所有结果。

之后如果配置了 API Key，同一首歌再分析一次，Gateway 会发现缓存里已经有这首歌的结果，但它是跳过了 L4 的，于是只补跑 L4，用现成的 L1 到 L3 结果生成解读，不重新计算前三层。补跑失败也不会让任务失败，只是保留原来跳过 L4 的结果。

## 6.2 工具调用循环

`orchestrator.py: run_explain` 实现了第 2.10.2 节讲的 Agent 循环：调用模型、执行工具、把结果交回模型，直到模型给出最后的回复。

### 初始化解读请求

```python
def run_explain(audio_id, language, feature_summary, understanding, aesthetic) -> AnalysisResult:
    language_name = LANGUAGE_NAMES.get(language, LANGUAGE_NAMES["en"])
    labels = DIMENSION_LABELS.get(language, DIMENSION_LABELS["en"])
    dimension_names = ", ".join(f'{dim}="{labels[dim]}"' for dim in DIMENSION_ORDER)
    system_prompt = (
        EXPLAIN_SYSTEM_PROMPT + f"\n\nAlways write summary and explanation in {language_name}. Do not mix languages. "
        f"Refer to each dimension by exactly this name, verbatim, every time it's mentioned: {dimension_names}."
    )

    tools = _openai_tools()
    messages: list[ChatCompletionMessageParam] = [
        ChatCompletionSystemMessageParam(role="system", content=system_prompt),
        ChatCompletionUserMessageParam(role="user", content=_build_context_message(feature_summary, understanding, aesthetic)),
    ]

    tool_call_log: list[ToolCallRecord] = []
    dimension_explanations: dict[str, str] = {}
    dimension_scores: dict[str, float] = {}
    model = os.environ["OPENAI_MODEL"]
```

准备阶段做了四件事：

1. **拼出系统提示词**：在固定的 `EXPLAIN_SYSTEM_PROMPT` 后面，追加这次请求的语言要求和四个维度的显示名称（第 6.4 节）。
2. **准备工具定义**：`_openai_tools()` 把注册表里的工具，转换成 OpenAI 接口要求的格式（第 6.3 节）。
3. **初始消息只有两条**：system 是系统提示词，规定任务和约束；user 是三份数据序列化成 JSON 后拼成的一段文字（第 6.4 节）。
4. **准备三个容器**，在循环中逐步填充：`tool_call_log` 记录每次成功的工具调用；`dimension_explanations` 按维度名存解释文字；`dimension_scores` 按维度名存分数。

模型名从环境变量 `OPENAI_MODEL` 读取。

### 单轮执行流程

```python
    turn = 0
    while True:
        turn += 1
        if turn > EXPLAIN_MAX_TURNS:
            summary_text = ""
            break

        response = _get_client().chat.completions.create(
            model=model,
            max_tokens=EXPLAIN_MAX_TOKENS,
            tools=tools,
            messages=messages,
        )
        message = response.choices[0].message
        message_dict = message.model_dump(exclude_none=True)
        messages.append(cast(ChatCompletionMessageParam, message_dict))

        if response.choices[0].finish_reason != "tool_calls":
            summary_text = (message.content or "").strip()
            break

        for tool_call in message.tool_calls or []:
            args = json.loads(tool_call.function.arguments)
            fn = TOOL_REGISTRY[tool_call.function.name]["fn"]

            start = time.monotonic()
            try:
                output = fn(args)
                is_error = False
            except ValueError as exc:
                output = {"error": str(exc)}
                is_error = True
            duration_ms = int((time.monotonic() - start) * 1000)

            if not is_error:
                tool_call_log.append(ToolCallRecord(tool_name=tool_call.function.name, input=args, output=output, duration_ms=duration_ms))
                dimension_explanations[args["dimension"]] = output["explanation"]
                dimension_scores[args["dimension"]] = float(args["score"])

            messages.append(
                ChatCompletionToolMessageParam(
                    role="tool",
                    tool_call_id=tool_call.id,
                    content=json.dumps(output, ensure_ascii=False),
                )
            )
```

每一轮做四件事：

1. **检查轮数。** 达到 10 轮上限后停止，原因见本节的「循环轮数上限」。
2. **调用模型，把回复追加到消息列表。** `chat.completions.create` 把整个消息列表和工具定义发给模型，`response.choices[0].message` 是模型这一轮的回复。`model_dump(exclude_none=True)` 把 SDK 的消息对象转成字典，去掉值为空的字段，再追加进 `messages`。
   注意要追加的是包含 `tool_calls` 的完整消息。下一轮发给模型时，模型要能看到"我上一轮调用了哪些工具、传了什么参数"；而且接口规定，每一条 tool 消息前面，都必须有一条包含对应 `tool_call_id` 的 assistant 消息，否则请求会被拒绝。
3. **检查 `finish_reason`。** 如果不是 `"tool_calls"`，说明模型认为任务已经完成，不再调用工具，它这一条回复的文字就是最后的总结，跳出循环。`message.content or ""` 是防御性的写法：如果模型返回的内容是空的，就当作空字符串处理。
4. **否则逐个执行工具。** 模型可能在一条回复里同时请求多次工具调用，`message.tool_calls` 是一个列表，逐个处理：

   - `json.loads(tool_call.function.arguments)`：模型给出的参数是一段 JSON 字符串，先解析成字典。
   - `TOOL_REGISTRY[...]["fn"]`：按工具名从注册表里找到对应的 Python 函数。
   - 执行函数，计时。如果抛出 `ValueError`，把错误信息包装成 `{"error": "..."}`（见下文）。
   - 成功的调用：追加一条记录到 `tool_call_log`，把解释文字和分数按维度名存起来。
   - 不管成功还是失败，都把结果作为一条 `tool` 消息追加进消息列表，带上对应的 `tool_call_id`，模型才知道这个结果对应的是哪一次调用。

   `message.tool_calls or []` 是防御性的写法：按接口约定，`finish_reason` 是 `"tool_calls"` 时这个列表一定有内容，但两个字段在类型上是独立的，类型检查器看不出这层关系。

### 消息列表的变化示例

项目第一次跑通时的日志显示，模型在第一轮的一条回复里，就同时请求了四次工具调用（耗时 13.5 秒），第二轮给出总结（耗时 2.8 秒），一共两轮。消息列表是这样增长的：

| 轮次 | 新增的消息 | `finish_reason` |
|---|---|---|
| 初始 | system、user | — |
| 第 1 轮 | assistant（请求 4 次 explain_dimension）、4 条 tool | `"tool_calls"` |
| 第 2 轮 | assistant（2 到 3 句总结） | `"stop"` |

模型也可以分几轮调用，比如每轮只调用一个维度，循环对这两种情况都能处理。代码里没有任何地方假设"一定是一轮调用四次"。

每一轮发给模型的，都是到目前为止的完整消息列表。所以第 2 轮时，模型能看到最初的数据、自己第 1 轮提交的四段解释，以及每段解释是否被工具接受，在此基础上写总结。

### 工具校验错误的回传

工具在参数不合法时会抛出 `ValueError`，比如维度名拼错、分数超出 0 到 100（第 6.3 节）。循环捕获这个异常后，不会让整个请求失败，而是把错误信息包装成 `{"error": "score out of range: 120"}` 这样的结果，作为这次工具调用的返回值发回给模型。模型在下一轮看到错误信息，可以修正参数后重新提交。

出错的调用不会写进 `tool_call_log`，也不会计入已完成的维度。

这里只捕获了 `ValueError`，也就是工具自己的格式检查。其他问题仍然会让请求失败：比如模型请求了一个注册表里不存在的工具名，或者参数里缺了某个字段，Python 会抛出 `KeyError`，不在捕获范围内。这类情况说明模型完全没有按工具定义调用，项目没有为它设计重试。

### 输出上限、调用超时与客户端懒加载

```python
EXPLAIN_MAX_TOKENS = 2048
CHAT_MAX_TOKENS = 1024
_LLM_TIMEOUT_SECONDS = 8 * 60
EXPLAIN_MAX_TURNS = 10
```

**输出上限 2048 个 token**

`max_tokens` 限制模型每一次回复最多生成多少个 token。一次解读要写四个维度的解释，如果模型在一条回复里提交全部四个，需要较多的输出空间。追问只回答一个问题，上限是 1024（第 6.6 节）。

**超时 8 分钟**

这个数字是和 Gateway 配合定的：

```python
# Kept below gateway/internal/data/engine_client.go's engineRequestTimeout (10
# minutes) so a slow LLM call fails here first, instead of Gateway cutting the
# connection while this call is still running unattended.
_LLM_TIMEOUT_SECONDS = 8 * 60
```

Gateway 调用 Engine 的每个内部接口，超时时间都是 10 分钟。Engine 为大模型客户端配置了 8 分钟的超时，比 Gateway 的 10 分钟短。这两个设置作用在不同层级。一次解读可能包含多轮模型请求，SDK 也可能重试，因此 Engine 仍可能在 Gateway 等待结束后才完成。

**客户端延迟创建**

```python
_client: OpenAI | None = None


def _get_client() -> OpenAI:
    global _client
    client = _client
    if client is None:
        client = OpenAI(
            api_key=os.environ["OPENAI_API_KEY"],
            base_url=os.environ["OPENAI_BASE_URL"],
            timeout=_LLM_TIMEOUT_SECONDS,
        )
        _client = client
    return client
```

大模型客户端在第一次调用时才创建，而不是在模块加载时。`main.py` 启动时会导入 `orchestrator.py`，如果在导入时就创建客户端，没有配置 API Key 时 `os.environ["OPENAI_API_KEY"]` 会直接报错，整个 Engine 进程都启动不了。延迟创建后，只有真正调用 L4 时才会报错；而 Gateway 在没有 API Key 时不会调用 L4（第 6.1 节）。

客户端用的是 OpenAI 的 SDK，但 `OPENAI_BASE_URL` 可以指向任何兼容这套接口的服务。

### 循环轮数上限

```python
# A normal run finishes in 2-3 turns (the four tool calls, then the summary).
# Without a cap, a model that never stops calling tools is only cut off by
# _LLM_TIMEOUT_SECONDS; stopping here leaves verified False for any dimension
# still missing and the summary empty.
EXPLAIN_MAX_TURNS = 10
```

正常情况下，循环两三轮就结束了。但如果模型一直调用工具、从不给出最后的总结，只要每轮都在超时前返回，客户端的超时设置就无法停止这个循环，因此还需要单独限制轮数。

如果第 10 轮结束时仍在请求工具，编排器会停止调用模型，保留已经提交的维度解读，总结留空。只要四个维度都已成功提交，`verified` 仍为真。

### 组装 AnalysisResult

循环结束后，把收集到的内容组装成 `AnalysisResult`：

```python
    explanation = "\n\n".join(
        f"**{labels[dim]} ({dimension_scores[dim]:.0f})**\n{dimension_explanations[dim]}"
        for dim in DIMENSION_ORDER
        if dim in dimension_explanations
    )

    return AnalysisResult(
        audio_id=audio_id,
        verified=len(dimension_explanations) == len(DIMENSION_ORDER),
        tool_call_count=len(tool_call_log),
        tool_call_log=tool_call_log,
        aesthetic=aesthetic,
        understanding=understanding,
        feature_summary=feature_summary,
        summary=summary_text,
        explanation=explanation,
        explanation_skipped=False,
    )
```

`explanation` 不是模型直接写的一整段文字，而是代码按固定顺序拼出来的：

- 按 `DIMENSION_ORDER` 的顺序（物理精确性、结构逻辑、情感深度、活力张力）遍历四个维度，跳过没有提交的。
- 每个维度一段：先是加粗的标题，由维度名和取整后的分数组成，比如 `**物理精确性 (77)**`；换行后是模型提交的解释文字。
- 段与段之间空一行。

所以第 1.3 节的解读里，每一段都以"**物理精确性 (77)**"这样的标题开头，四个维度的顺序总是固定的，不受模型调用工具的顺序影响。标题里的分数是模型提交时传入的 `score`，取整到个位。前端用 Markdown 渲染这段文字，`**` 之间的内容显示为粗体。

`verified`、`tool_call_count`、`tool_call_log` 三个字段的含义，见第 6.5 节。

## 6.3 解读提交工具:explain_dimension

### 工具注册表与参数定义

L4 只给模型提供了一个工具，定义在 `registry.py`：

```python
def _explain_dimension_entry() -> dict:
    return {
        "fn": explain_dimension,
        "schema": {
            "name": "explain_dimension",
            "description": "Submit an evidence-based natural-language explanation for one aesthetic dimension",
            "input_schema": {
                "type": "object",
                "properties": {
                    "dimension": {
                        "type": "string",
                        "enum": ["physical_precision", "structural_logic", "emotional_depth", "vital_tension"],
                        "description": "The aesthetic dimension's English name",
                    },
                    "score": {"type": "number", "description": "That dimension's score, 0-100"},
                    "evidence": {"type": "object", "description": "That dimension's evidence value dict"},
                    "explanation": {
                        "type": "string",
                        "description": "Natural-language explanation, must cite concrete values from evidence, must not invent numbers",
                    },
                },
                "required": ["dimension", "score", "evidence", "explanation"],
            },
        },
    }


TOOL_REGISTRY: dict[str, dict] = {
    "explain_dimension": _explain_dimension_entry(),
}
```

注册表 `TOOL_REGISTRY` 是一个字典，键是工具名，值有两部分：

- `fn`：真正执行的 Python 函数，循环里按工具名找到它（第 6.2 节）。
- `schema`：给模型看的工具说明，用 JSON Schema 描述参数（第 2.10.2 节）。

工具的描述是"为一个美学维度提交一段有证据支撑的自然语言解释"。四个参数：

| 参数 | 类型 | 说明 |
|---|---|---|
| `dimension` | 字符串，只能是四个值之一 | 维度的英文名。`enum` 限定了取值范围 |
| `score` | 数 | 这个维度的分数，0 到 100 |
| `evidence` | 对象 | 这个维度的证据字典 |
| `explanation` | 字符串 | 解释文字，必须引用证据里的具体数值，不能编造数字 |

四个字段都在 `required` 里。参数的 `description` 是写给模型看的：模型读到"must cite concrete values from evidence"，就知道写解释时要引用证据。

### 工具的参数校验与返回值

```python
VALID_DIMENSIONS = {"physical_precision", "structural_logic", "emotional_depth", "vital_tension"}


def explain_dimension(args: dict) -> dict:
    dimension = args["dimension"]
    score = args["score"]
    evidence = args["evidence"]
    explanation = args["explanation"]

    if dimension not in VALID_DIMENSIONS:
        raise ValueError(f"invalid dimension: {dimension!r}")
    if not (0 <= score <= 100):
        raise ValueError(f"score out of range: {score!r}")
    if not isinstance(evidence, dict) or not evidence:
        raise ValueError("evidence must be a non-empty object")
    if not explanation.strip():
        raise ValueError("explanation is empty")

    return {"explanation": explanation}
```

这个函数只做四项检查：

1. 维度名是不是四个合法值之一。
2. 分数是不是在 0 到 100 之间。
3. 证据是不是一个非空的字典。
4. 解释文字去掉首尾空白后是不是空的。

任何一项不通过，就抛出 `ValueError`，循环会把错误信息发回给模型（第 6.2 节）。全部通过后，把模型写好的解释**原样返回**。

Schema 里已经用 `enum` 限定了维度名，为什么函数里还要再检查一次？因为 Schema 只是告诉模型"应该怎么传"，模型不一定照做。代码层面的检查，才能保证不合法的参数进不了结果。

### 通过工具提交模型生成的解读

通常给模型一个工具，是为了给它一种它本来没有的能力：

- 模型不知道今天的天气，给它一个查天气的工具。
- 模型算不准大数乘法，给它一个计算器。
- 模型不知道数据库里有什么，给它一个查询数据库的工具。

这些工具的共同点是：工具执行之前，模型不知道答案；工具执行之后，模型才第一次得到这个信息。

`explain_dimension` 完全不是这样。它被调用时，解释文字已经是模型自己写好的了，作为参数传进来；工具检查一下格式，再原样还回去，没有给模型任何新信息。

### 按维度收集解读与记录调用

如果只是让模型写一段解读，直接让它输出一大段文字就行了。用工具调用来提交，换来的是三样东西：

**结构化**

每一段解释都和某一个维度、某一个分数、某一份证据绑定在一起。系统明确知道"这段话解释的是结构逻辑"，不需要再用正则表达式或者再调一次大模型，从一大段文字里把各个维度的内容拆出来。

**可清点**

代码用一个字典收集每个维度的解释：

```python
dimension_explanations[args["dimension"]] = output["explanation"]
```

最后只需要数一下字典里有没有四个维度，就能确定地知道模型有没有漏掉某个维度（第 6.5 节）。如果是一整段自由文本，没法做这种确定性的检查：要判断"这段文字有没有讲到情感深度"，本身又是一个需要理解语言的问题。

**可审计**

每一次成功的工具调用都会生成一条记录，包括工具名、输入参数、输出、耗时。不管模型最后的总结怎么说，记录里留下的是它每一步实际提交了什么。

可以把这种用法称为"强制结构化提交"：工具不是能力的来源，而是一道格式关卡。它存在的意义，不是做了模型做不到的事，而是让模型的输出必须经过一个可以检查的环节。项目的设计笔记 `articles/principles/01-tool-use-as-structured-audit.md` 专门讨论了这个设计。

### 工具契约与实现的维护顺序

`explain_dimension` 由三个文件组成，项目的 `CLAUDE.md` 规定了它们的修改顺序：

1. **`TOOL.md`**：设计文档，写明工具的职责、输入输出的结构、验收清单和已知局限。
2. **`explain_dimension.py`**：实现函数。
3. **`registry.py`**：把函数和 Schema 注册进去，循环才能找到它。

改工具时，必须先改 `TOOL.md`，再改实现和注册表。`TOOL.md` 开头特别说明：这个文件在运行时不会被任何代码读取，`registry.py` 里的 Schema 是从这里手动抄过去的，两者的一致靠流程约定保证，不靠工具自动同步。

### 将工具定义转换为 SDK 格式

`registry.py` 里的 Schema 用的是一种中性的格式：`name`、`description`、`input_schema`。它并不是 OpenAI SDK 要求的格式，OpenAI 要求的字段名是 `parameters`，而且外面还要再包一层 `type="function"`。转换由 `orchestrator.py: _openai_tools` 完成：

```python
def _openai_tools() -> list[ChatCompletionFunctionToolParam]:
    tools: list[ChatCompletionFunctionToolParam] = []
    for entry in TOOL_REGISTRY.values():
        schema = entry["schema"]
        tools.append(
            ChatCompletionFunctionToolParam(
                type="function",
                function=FunctionDefinition(
                    name=schema["name"],
                    description=schema["description"],
                    parameters=schema["input_schema"],
                ),
            )
        )
    return tools
```

遍历注册表里的每个工具，把 `input_schema` 放到 `parameters` 的位置，包装成 OpenAI 的工具定义。

更换 SDK 时，工具定义可由转换函数生成，工具的实现和注册表可以复用。消息格式以及工具结果如何回传，仍由编排器按对应接口处理。

### 工具校验的边界

工具只检查格式，不检查内容。`TOOL.md` 的"已知局限"里写明了两点：

- **不核对解释里的数字。** 它不会检查解释里提到的数字，是否真的和 `evidence` 里的值一致。这一点完全依赖系统提示词的约束（第 6.4 节）。
- **不防重复提交。** 同一个维度提交两次，两次都会被接受。

另外，工具也不会把模型提交的 `score`、`evidence` 和 L3 的原始结果比对，只检查分数在 0 到 100 之间。第 6.5 节列出了可补充的校验方法。

## 6.4 系统提示词设计

`system_prompt.py` 里有两套系统提示词：`EXPLAIN_SYSTEM_PROMPT` 用于生成解读，`CHAT_SYSTEM_PROMPT` 用于回答追问（第 6.6 节）。两套都用英文写成，这一节先讲生成解读用的那一套，以及它配合的上下文。

### 将分析结果加入上下文

```python
def _build_context_message(
    feature_summary: FeatureSummary,
    understanding: UnderstandingBundle,
    aesthetic: AestheticBundle,
) -> str:
    return (
        "Here is the complete analysis data (JSON) for this track — complete the task based on this data:\n\n"
        f"feature_summary:\n{json.dumps(asdict(feature_summary), ensure_ascii=False, indent=2)}\n\n"
        f"understanding:\n{json.dumps(asdict(understanding), ensure_ascii=False, indent=2)}\n\n"
        f"aesthetic:\n{json.dumps(asdict(aesthetic), ensure_ascii=False, indent=2)}"
    )
```

三份数据各自用 `asdict` 转成字典，再用 `json.dumps` 序列化成带缩进的 JSON，拼成一条 user 消息。开头一句话告诉模型："这是这首歌完整的分析数据，基于这些数据完成任务。"

`ensure_ascii=False` 让中文等非 ASCII 字符原样保留，而不是转成 `中` 这样的转义码。`indent=2` 让 JSON 分行缩进，模型更容易看清层级。

模型能看到的所有数字都在这里。拿到的上下文大致是这样的（节选）：

```json
feature_summary:
{
  "bpm": 136.0,
  "tempo_stability": 0.03,
  "key": "G major",
  ...
}

aesthetic:
{
  "physical_precision": {
    "score": 55.05,
    "evidence": {"tempo_stability": 0.03, "dynamic_range_db": 11.87, "frequency_balance_std_db": 13.82}
  },
  ...
}
```

L1 到 L3 在返回结果前为相关数值保留两位小数，分别见第 3.11 节、第 4 章的「L2 分析接口」和第 5.1 节。`understanding` 里的情感弧线、和弦列表这类长数据也会完整放进来，一首 29 分钟的歌，情感弧线就有上千个点。这份上下文的长度，基本由歌曲时长决定。

### 解读任务的定义

`EXPLAIN_SYSTEM_PROMPT` 一开始先交代身份和任务：

```
You are the explanation engine of a music aesthetics analysis system.

You have received the complete audio analysis result:
- feature_summary: L1 signal features (BPM, key, dynamic range, etc.)
- understanding: L2 semantic labels (genre, emotion arc, instruments, structure, chords)
- aesthetic: L3 aesthetic scores (four dimension scores and each dimension's evidence)

This data was already produced by deterministic computation modules. Your task: based on these
results, generate a well-evidenced natural-language explanation for each aesthetic dimension.
```

意思是：你是一个音乐美学分析系统的解释引擎；你收到了三份数据，分别是什么；这些数据已经由确定性的计算模块算好了，你的任务是基于它们，为每个维度写出有证据支撑的解释。

### 解读的七条约束

接下来是七条约束，每一条约束的是一种具体的问题。

1. **数字只能来自上下文。** 解读里出现的每个数字，都必须来自三份数据，不能凭直觉或常识补充。这是整个 L4 设计的核心约束，对应第 2.10.1 节讲的幻觉问题。
2. **四个维度必须各调用一次工具。** 每次调用传入这个维度自己的分数和证据，解释里必须引用证据中的具体数值。这一条和工具设计配合：工具保证每次提交的格式合法，这一条要求模型把四个维度都提交。
3. **最后只输出 2 到 3 句总结。** 四个维度的详细解释已经通过工具提交了，最后的回复只需要说明哪个维度最突出、为什么，不能重复四个维度的内容。还有两点要求：
   - 明确告诉模型四个维度没有综合分，不能编造或暗示一个总分（第 5.1 节）。
   - 直接输出纯文本，不要 JSON、不要 Markdown 代码块、不要 `summary` 这样的字段名。
4. **不能照抄字段名。** `tempo_stability`、`dynamic_range_db` 这些是 JSON 的键名，不是给人看的术语。每个值都必须用回复所用的语言转述，比如"速度稳定度为 0.03"，而不是"tempo_stability 是 0.03"。BPM 这类通用缩写可以保留，但字段名本身不是专业术语，必须转述。
5. **每个数字都要带单位和含义。** 不知道字段含义的读者，看到一个光秃秃的数字毫无意义。所以每个数字后面要用括号说明单位和含义，比如"爆发密度达到 278.93（每分钟的起音事件数）"，"段落均衡比为 0.69（0 到 1 的比例……）"。这一条适用于所有出现数字的地方，包括四个维度的解释和最后的总结。
   这一条还专门补充了一个语法要求：括号不能硬插在数字和它修饰的名词之间。要先写出完整的句子，再确认加上括号后仍然通顺；如果不通顺，就调整句子结构，而不是硬把括号塞进去。第 1.3 节的解读里，每个数字后面都跟着这样一个括号，就是这一条的效果。
6. **修饰词要和指标的方向一致。** 有的指标越大越好，比如动态范围；有的越小越好，比如拍速的不稳定程度、极性切换率。选择"仅""高达"这类修饰词之前，要先判断这个数字对这个指标来说是好是坏：
   - 一个越小越好的指标数值很小，这是好事，不能说"仅为"。
   - 一个越大越坏的指标数值很大，这是坏事，不能说"高达"。
   修饰词要跟着"这个数对这个指标是好是坏"走，而不是跟着"这个数看起来大还是小"走。
7. **已知的测量盲区，要按"这个指标测到了什么"来表述。** 第 5 章的两个盲区写进了提示词：
   - 物理精确性的频率均衡度、活力张力的两个子指标，天然偏向全编制、高动态对比的编曲。安静、连续、编制稀疏的作品（独奏、氛围音乐、极简制作），不管演奏得多好，在这些子指标上都会偏低。如果证据和乐器构成指向这种情况，应该说"这首作品的织体和动态在这个维度上测得较低"，而不是"演奏或制作有不足"（第 5.2 节、第 5.5 节）。
   - 情感深度会把任何效价、唤醒度的起伏都当作情绪变化，包括 EDM 那种纯靠能量堆叠的唤醒度上升。如果流派和乐器指向这种情况，不能把高分说成叙事或和声深度的证明，而要描述为"持续的唤醒度变化"（第 5.4 节）。

### 禁止事项

提示词最后还有一个"禁止事项"清单，把上面几条用反面的形式再列一遍：

- 上下文里没有的数字。
- 没有说明单位和含义的数字。
- 破坏句子语法的括号。
- 价值判断和指标方向相反的修饰词。
- 跳过某个维度的工具调用。
- 自行推断数据，比如说"速度很稳"，必须有 `tempo_stability` 的值支撑。
- 把最后的总结包装成 JSON 或其他结构化格式。
- 照抄英文字段名，而不是转述。

正面写一遍"应该怎么做"，反面再列一遍"不能做什么"，是给模型的双重提示：模型对明确列出的禁止项通常更敏感。

### 解读中的指标误读

第 1.3 节引用的那段解读，是在这七条约束都生效的情况下生成的，仍然读错了两个数字的含义：

- 把 T-S-D 覆盖率 0.84 解释成"可被段落与转折模型解释的部分"。实际含义是 84% 的和弦属于主、下属、属三种功能（第 5.3 节）。
- 把段落长度的变异系数 0.41 说成"越接近 1 越均匀"。实际上它越小越均匀。

第二个错误恰好违反的是第 6 条：模型没有先判断这个指标的方向，而是根据"均衡比"这个名字，想当然地认为越大越均衡。

这两个错误有一个共同点：数字本身是对的，都来自证据，第 1 条约束起了作用；错的是对数字含义的理解。而模型能看到的只有字段名和数值，字段的定义它并不知道，只能从名字猜。这说明提示词能降低出错的概率，但不能保证不出错。要真正挡住这类问题，需要在上下文里给出每个字段的明确定义，或者在代码层面做检查，第 6.5 节会讨论。

### 如何指定回复语言

```python
# Appended to EXPLAIN_SYSTEM_PROMPT/CHAT_SYSTEM_PROMPT per request instead of
# keeping separate zh/en prompt copies that could drift out of sync.
LANGUAGE_NAMES = {"zh": "Chinese (中文)", "en": "English"}
```

系统支持中文和英文两种解读，由用户在网页上选择的语言决定。但提示词本身只有一份英文版本，语言要求在每次请求时追加到末尾（第 6.2 节的准备阶段）：

```
Always write summary and explanation in Chinese (中文). Do not mix languages.
```

如果维护中英两份提示词，以后改了一份，很容易忘记同步另一份，两种语言的解读就会遵守不同的规则。只维护一份，再追加语言要求，就不会出现这个问题。默认用英文。

同一首歌的中文解读和英文解读，是两次独立的分析：Gateway 的缓存键里带着语言（第 1.4 节），第一次用另一种语言分析一首歌时，L1 到 L4 会全部重新计算。

### 各语言的维度显示名称

追加的内容里还有每个维度的显示名称，来自 `orchestrator.py` 里的 `DIMENSION_LABELS`：

```python
DIMENSION_LABELS = {
    "zh": {
        "physical_precision": "物理精确性",
        "structural_logic": "结构逻辑",
        "emotional_depth": "情感深度",
        "vital_tension": "活力张力",
    },
    "en": {
        "physical_precision": "Physical Precision",
        "structural_logic": "Structural Logic",
        "emotional_depth": "Emotional Depth",
        "vital_tension": "Vital Tension",
    },
}
```

中文请求时，追加到提示词末尾的是：

```
Refer to each dimension by exactly this name, verbatim, every time it's mentioned: physical_precision="物理精确性", structural_logic="结构逻辑", emotional_depth="情感深度", vital_tension="活力张力".
```

如果不指定，模型每次都会自己翻译 `vital_tension`，一会儿叫"生命张力"，一会儿叫"活力张力"，同一份解读里前后都可能不一致。把名称写进提示词，并要求"每次都原样使用"，模型就只会用这一个名字。

这份名称还被复用了一次：第 6.2 节组装 `explanation` 时，每段的标题也用 `labels[dim]`。模型写的正文和代码拼的标题，用的是同样的显示名称。

## 6.5 解读提交状态与工具调用记录

`run_explain` 返回的 `AnalysisResult` 里，有三个字段记录解读的提交状态和成功的工具调用。

```python
return AnalysisResult(
    audio_id=audio_id,
    verified=len(dimension_explanations) == len(DIMENSION_ORDER),
    tool_call_count=len(tool_call_log),
    tool_call_log=tool_call_log,
    ...
)
```

- **`verified`**：`dimension_explanations` 里是否正好有四个维度，也就是四个维度是否都成功提交了解释。
- **`tool_call_count`**：`tool_call_log` 的长度，即成功的工具调用次数。正常情况下是 4。
- **`tool_call_log`**：每一次成功调用的详细记录。

每条记录是一个 `ToolCallRecord`，有四个字段：

| 字段            | 内容                            |
| ------------- | ----------------------------- |
| `tool_name`   | 工具名，这里永远是 `explain_dimension` |
| `input`       | 模型传入的全部参数：维度、分数、证据、解释         |
| `output`      | 工具的返回值，也就是原样返回的解释             |
| `duration_ms` | 工具执行耗时（毫秒）                    |

`tool_call_log` 是一份不依赖模型自我描述的客观记录。它会随分析结果一起存进数据库，事后可以逐条查看模型在每一步实际提交了什么。

### 结果页的调用记录与校验标记

结果页"AI 分析"标签页的顶部有一行标记：

- **"4 项工具调用"**：鼠标悬停时，弹出 `tool_call_log` 的内容，列出每次调用提交的维度、分数和证据。这个弹窗固定用英文显示，因为它是给想核对细节的人看的技术记录。
- **"✓ 已校验"**：只在 `verified` 为真时显示。

下面是 `summary` 和 `explanation`（按 Markdown 渲染）。如果 `explanation_skipped` 为真，这些都不显示，只显示"尚未配置 OPENAI_API_KEY，该功能不可用"（第 6.1 节）。

### 可补充的数值核对与指标说明

这些边界都可以用代码进一步约束：

- **核对数字**：在工具里用正则表达式提取解释中的数字，再与允许引用的上下文数值核对。数值比较需要考虑取整、单位换算和百分数的写法。`TOOL.md` 的已知局限里也写了这个方向。
- **核对分数和证据**：把模型提交的 `score`、`evidence`，和请求里 `aesthetic` 的原始值直接比较，不一致就返回错误。
- **给出字段定义**：在上下文里为每个证据字段附上一句定义，比如"segment_balance_ratio：段落时长的变异系数，越小越均匀"，让模型不必从字段名猜含义。

## 6.6 追问:无状态的单轮问答

用户看完解读后，可以在结果页的输入框里继续提问，比如"为什么这首歌的情感深度不高"。

### 追问的请求流程

1. 浏览器把问题和当前的界面语言发给 Web 的 `/api/chat/{id}` 路由，Web 原样转给 Gateway（第 1.4 节）。
2. Gateway 按任务 ID 从数据库取出这首歌已经存好的 `AnalysisResult`。如果还没有分析结果，直接返回错误。
3. Gateway 把问题、语言，加上分析结果里的三份数据、`summary`、`explanation`，一起发给 Engine 的 `/internal/chat`。
4. Engine 的 `run_chat` 调用一次大模型，返回回答。

Gateway 这一步的代码很短：

```go
func (s *JobService) Chat(ctx context.Context, jobID, question, language string) (answer string, err error) {
    job, err := s.jobStore.GetJob(ctx, jobID)
    if err != nil {
        return "", err
    }
    if job.Result == nil {
        return "", ErrJobNotAnalyzed
    }
    result := job.Result
    return s.engine.Chat(ctx, biz.EngineChatRequest{
        AudioID:        result.AudioID,
        Question:       question,
        Language:       language,
        FeatureSummary: &result.FeatureSummary,
        Understanding:  &result.Understanding,
        Aesthetic:      &result.Aesthetic,
        Summary:        result.Summary,
        Explanation:    result.Explanation,
    })
}
```

### 按请求重建上下文

```python
def _build_chat_context_message(feature_summary, understanding, aesthetic, summary, explanation) -> str:
    return (
        _build_context_message(feature_summary, understanding, aesthetic)
        + "\n\nHere are the conclusions already generated for this data — when answering the "
        "follow-up question, you may only reference the information in this data:\n\n"
        + f"summary:\n{summary}\n\n"
        + f"explanation:\n{explanation}"
    )
```

追问的上下文在生成解读的上下文（第 6.4 节）后面，再接上已经生成的总结和四个维度的解释，中间一句话告诉模型："这些是已经为这份数据生成的结论，回答追问时，只能引用这里的信息。"

```python
def run_chat(audio_id, question, language, feature_summary, understanding, aesthetic, summary, explanation) -> str:
    language_name = LANGUAGE_NAMES.get(language, LANGUAGE_NAMES["en"])
    system_prompt = CHAT_SYSTEM_PROMPT + f"\n\nAlways answer in {language_name}. Do not mix languages."

    messages: list[ChatCompletionMessageParam] = [
        ChatCompletionSystemMessageParam(role="system", content=system_prompt),
        ChatCompletionUserMessageParam(
            role="user",
            content=_build_chat_context_message(feature_summary, understanding, aesthetic, summary, explanation),
        ),
        ChatCompletionUserMessageParam(role="user", content=question),
    ]

    response = _get_client().chat.completions.create(
        model=os.environ["OPENAI_MODEL"],
        max_tokens=CHAT_MAX_TOKENS,
        messages=messages,
    )
    message = response.choices[0].message
    return (message.content or "").strip()
```

消息列表只有三条：

1. system：追问用的系统提示词，加上语言要求。
2. user：完整的上下文。
3. user：用户的问题。

问题单独作为一条消息，而不是拼进上下文里，这样模型能清楚地分辨"哪些是参考资料，哪些是要回答的问题"。

和生成解读相比，有三处不同：

- **只调用一次模型，没有循环**。
- **不提供任何工具**：调用时没有传 `tools` 参数，模型只能直接用文字回答。四个维度的分数和解释已经生成好了，追问只需要基于这些结果回答具体的问题。
- **输出上限是 1024 个 token**：回答一个问题，不需要生成解读那么多的空间。

追问的语言由界面语言决定。用户把界面切换成英文后再提问，回答也会是英文，即使原来的解读是中文。

### 每次追问独立处理

一般的聊天机器人需要保存会话：记住用户之前问过什么，下一次把历史消息一起发给模型（第 2.10.1 节：模型本身不记得之前的请求）。

本项目的追问是无状态的。每次请求，Gateway 都把这首歌的完整分析结果和用户的问题一起发给 Engine，Engine 不保存任何东西，回答完就结束。系统提示词里也明确写了："每次回答都是独立的一轮，不要假设用户之前问过什么，也不要记住这次的回答留给以后用。"

这样做的好处是简单：

- 不需要会话 ID，不需要存储聊天记录，也不需要考虑会话什么时候过期。
- Engine 重启、多个 Engine 实例之间切换，都不影响追问。
- 和 L1 到 L3 一样，Engine 在两次请求之间不保存任何数据（第 1.4 节）。

代价是不支持多轮对话：每个问题都是独立回答的，用户不能说"你刚才提到的那个数字是什么意思"，因为模型看不到"刚才"的回答。对"针对一份分析结果提问"这个场景，单轮问答已经够用。

### 追问回答的约束

`CHAT_SYSTEM_PROMPT` 有六条约束，大部分继承自生成解读时的规则：

1. 只能引用上下文里的数值和结论，不能编造新的数字或结论。
2. 不需要调用任何工具，基于已有结果回答。
3. 每次回答都是独立的一轮。
4. 不能照抄字段名。
5. 每个数字都要带单位和含义。
6. 涉及有测量盲区的维度时，要沿用解读里已有的说法。

最后一条是追问特有的要求：

> If the question concerns one of these dimensions and the evidence/genre suggests this pattern, answer with the same measurement-pattern framing already used in `explanation` — don't contradict it by reasoning fresh from the raw number.

意思是：如果问题涉及有测量盲区的维度，回答要沿用解读里已有的说法，不能从原始数字重新推理，得出相反的结论。比如解读里已经说了"这首独奏曲在活力张力上测得较低，反映的是织体特点，不是演奏不足"，追问时就不能再说"活力张力低说明这首曲子缺乏张力"。

## 6.7 本章小结

L4 把前三层的分析结果交给大模型。模型根据分数和证据撰写四个维度的解释，通过 `explain_dimension` 分别提交，再用几句话总结整首曲目的分析结果。每次成功的工具调用都会留下记录，可以查到模型当时提交的分数、证据和解释。

`verified` 为真表示四个维度的解读都已提交并通过参数检查。解释是否准确，仍需对照原始证据和指标定义。
